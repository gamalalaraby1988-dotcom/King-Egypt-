# سجل فحص الطلبات المتوازية لاقتصاد الاختبار

**النطاق:** مشروع Supabase التجريبي `KING_OF_EGYPT_CITY_TEST`، مخطط `game_test` فقط.  
**التاريخ:** 2026-11-13  
**الفرع:** `supabase-free-test-environment`

## الغرض

توثيق فحص وظيفي لسلامة نموذج `apply_test_delta` عند إرسال عدة طلبات منسقة بالتوازي من جهة الاختبار. استُخدمت حسابات UUID اصطناعية، ولم تُستخدم حسابات لاعبين أو أرصدة حقيقية.

- الرصيد الابتدائي: 0.
- أُرسلت 12 عملية إضافة، كل واحدة بقيمة +1 وبمفتاح idempotency مستقل.
- جميع الاستدعاءات الـ12 أعادت نجاحًا مع `applied=true`.
- الرصيد النهائي المرصود: 12.
- عدد سجلات ledger: 12.
- عدد مفاتيح ledger المميزة: 12.
- عدد سجلات idempotency: 12.

**النتيجة:** لا توجد إضافة مفقودة أو مكررة في هذا الفحص.

## حدود هذا الدليل

أُطلقت استدعاءات SQL عبر أداة الاتصال في دفعتين باستخدام تنفيذ متزامن من جهة المنسق (`Promise.all`). لا توفر هذه الطريقة إثباتًا قاطعًا بأن كل استدعاء استخدم اتصال PostgreSQL مستقلًا ومتداخلًا زمنيًا؛ لذلك فهذا **فحص طلبات متوازية على مستوى المنسق** وليس اختبار ضغط أو اختبار تزامن إنتاجي متعدد الاتصالات.

لم يُختبر بعد:
- التزامن الحقيقي عبر جلسات PostgreSQL مستقلة مع حواجز بدء متزامنة.
- حمل مرتفع وقياس زمن الاستجابة ومعدل التعارضات.
- انقطاع الشبكة بعد نجاح COMMIT وإعادة المحاولة.
- deadlocks والتعافي تحت ضغط.
- المصادقة وواجهات API من عميل اللعبة.

## تنظيف الاختبار

حُذفت حسابات الاختبار الاصطناعية وسجلاتها بعد التحقق. وأكد الاستعلام النهائي أن الجداول الثلاثة فارغة:
- wallets: 0
- ledger: 0
- idempotency_requests: 0

## الحكم

نجح الفحص الوظيفي المبدئي لعدم فقد الإضافات ولمنع تكرار المفتاح الواحد ضمن نطاق الاستدعاءات المنفذة. لا يُعد ذلك اعتمادًا إنتاجيًا، ولا يغيّر حقيقة أن ربط Godot وخدمة API والمصادقة واختبار التزامن الحقيقي ما زالت غير منفذة.
