# خدمة استقبال مزامنة اللاعب — إعداد ومراجعة

**الحالة:** ملفات مصدر ضمن PR #38. Migration `player_account_provisioning` مطبّقة على قاعدة الإنتاج بالإصدار `20261119154243`. Migration صندوق أحداث المزامنة مطبقة في مشروع الاختبار فقط، ولم تُطبق على الإنتاج. Edge Function `player-sync` منشورة بنجاح في مشروع الاختبار (الإصدار 1، ACTIVE، `verify_jwt=false` مع تحقق صريح من access token داخل الدالة)، ولم تُنشر على الإنتاج.

## المكونات

- تسجيل/دخول عام للاعبين عبر بريد OTP من Supabase Auth، مع إنشاء المستخدم الجديد تلقائيًا عند عدم وجوده.
- عميل `scripts/player_account_auth_client.gd` مستقل عن `FounderAuthClient`، ويحفظ Refresh Token للاعب في Android Keystore باستخدام alias مختلف عن Alias المؤسس.
- Migration `20261119154243_player_account_provisioning.sql` تنشئ ملف لاعب برمز فريد من 10 خانات ومحفظة بأرصدة صفرية عند إنشاء حساب Auth، وتستكمل الملفات/المحافظ الناقصة للحسابات الحالية بشكل idempotent.
- واجهة تسجيل الدخول العامة تعرض البريد ومعرّف الحساب ورمز اللاعب، ولا تمنح أي صلاحية مؤسس.

- عميل Godot: `scripts/player_sync_client.gd` مع قائمة انتظار محلية `user://player_sync_outbox.cfg`، ومعرّفات UUID ثابتة، ودفعات حتى 50 حدثًا، وحذف الحدث من القائمة فقط بعد تأكيد الخادم. عند فشل الحفظ بعد القبول يمكن إعادة الإرسال بأمان بفضل مفتاح idempotency.
- ربط دورة جلسة المصادقة الحالية في `main.gd` مع العميل؛ يتم تمرير access token فقط، ولا يغادر refresh token مخزن Android الآمن.

- Migration: `20261119160000_player_sync_inbox.sql`
- Edge Function: `player-sync`
- RPC: `public.submit_player_sync_events(jsonb)`
- التخزين: `private.player_sync_events`

## حدود البيانات

تُقبل فقط أحداث:
- `setting_changed`: إعدادات مسموح بها (اللغة، حساسية الكاميرا، الصوت، تخطيط التحكم).
- `mission_progress_observed`
- `achievement_progress_observed`
- `activity_progress_observed`

أحداث التقدم مجرد ملاحظات غير موثوقة من العميل. لا تمنح خبرة أو مكافآت ولا تثبت إكمالًا. لا تقبل الخدمة المال أو الجواهر أو الرقائق أو الملكيات أو إيصالات الشراء أو صلاحيات المؤسس.

## الحماية

- Edge Function تستخدم `verify_jwt = false` لأن المفتاح العام من النوع `sb_publishable`؛ لذلك تتحقق الدالة بنفسها من access token عبر `GET /auth/v1/user` قبل أي وصول للبيانات.
- المفتاح `sb_publishable` يُقرأ من كائن `SUPABASE_PUBLISHABLE_KEYS` تحت الاسم `default` ويُرسل في `apikey` فقط، ورمز المستخدم في `Authorization: Bearer`.
- RPC تستخرج هوية الحساب من `auth.uid()` ولا تستقبل user_id من العميل.
- جدول التخزين في schema خاصة غير مكشوفة عبر Data API، ولا توجد صلاحيات مباشرة للأدوار العامة.
- RPC بصلاحية `SECURITY INVOKER` و`search_path = ''`، وتعتمد على RLS وسياسة إدخال تقصر `user_id` على `auth.uid()`؛ لا تستخدم صلاحيات مالك الجدول لتجاوز RLS.
- قيد فريد `(user_id, event_id)` يجعل إعادة الإرسال آمنة من التكرار.
- الدفعة لا تتجاوز 50 حدثًا، وحجم payload لا يتجاوز 8 KiB لكل حدث، ويُفرض حد جسم HTTP البالغ 512 KiB أثناء القراءة المتدفقة.
- قفل معاملات لكل لاعب يحد الاستقبال إلى 200 حدث مقبول خلال نافذة متحركة مدتها 5 دقائق.
- مفاتيح التقدم محصورة في نطاقات `mission.*` و`achievement.*` و`activity.*` بحسب نوع الحدث.
- مهمة pg_cron يومية تحذف أحداث المزامنة الأقدم من 30 يومًا.

## مفتاح التشغيل

- `player_sync/enabled` مضبوط على `false` افتراضيًا في `project.godot`.
- لن يرسل عميل Godot أي طلبات حتى بعد تسجيل الدخول ما لم يُفعّل هذا المفتاح صراحة بعد نشر قاعدة البيانات والدالة واختبارهما.
- إبقاء المفتاح مغلقًا يحافظ على قائمة الانتظار المحلية ويمنع استدعاء endpoint غير منشور.

## حالة النشر والاختبار

- نُشرت Edge Function `player-sync` في مشروع `KING_OF_EGYPT_CITY_TEST` فقط، الإصدار 1 والحالة ACTIVE، باستخدام المصدر الموجود في هذا الفرع.
- لم يُجرَ استدعاء HTTP فعلي بعد؛ لا توجد نتيجة runtime تثبت نجاح طلب مصادق أو رفض رمز غير صالح. أداة Supabase المتاحة هنا تدعم النشر وقراءة تفاصيل الوظيفة والسجلات، لكنها لا توفر عميل HTTP لاستدعائها مباشرة.
- لم تُنشر الوظيفة أو migration صندوق الأحداث على الإنتاج، ولم يتغير إعداد `player_sync/enabled=false` في اللعبة.

## نشر آمن — خطوات الإنتاج غير منفذة

1. مراجعة SQL وEdge Function في PR، مع اعتبار ترحيل إنشاء الحسابات مطبقًا بالفعل على الإنتاج.
2. تطبيق Migration صندوق الأحداث `20261119160000_player_sync_inbox.sql` في بيئة تطوير أولًا؛ لا تُعد تطبيق Migration إنشاء الحسابات على الإنتاج لأنها مطبقة بالفعل.
3. التحقق من أن schema `public` تسمح باستدعاء RPC عبر Data API، وأن الدالة `player-sync` تتحقق من JWT للمستخدم صراحةً عبر Supabase Auth، ثم تمرر الرمز نفسه إلى RPC لتطبيق `auth.uid()` وRLS، وأن مهمة pg_cron الخاصة بالتنظيف موجودة وتعمل.
4. نشر Edge Function بعد موافقة مستقلة.
5. إجراء اختبار بحساب اختبار عادي: إرسال حدث مسموح، إعادة event_id نفسه، محاولة مستخدم غير مصادق، ومحاولة payload مالي/ملكية يجب رفضها.
6. تشغيل Supabase Security Advisors بعد تغييرات DDL.
7. لا تُربط اللعبة بإرسال أحداث الإنتاج قبل إتمام الاختبارات ومراجعة قواعد قبول تقدم المهام والمكافآت.

## ملاحظة API

من 30 أكتوبر 2026 لم تعد الجداول الجديدة في `public` تُعرّض تلقائيًا عبر Data API. هذا التصميم يخزن البيانات في schema `private` ويستدعي RPC ضمن `public`. يجب التأكد من أن `public` مفعّل ضمن exposed schemas وأن صلاحية EXECUTE للدالة تصل إلى authenticated؛ لا حاجة إلى تعريض schema `private`.

## التحقق

اجتازت النسخة المعدلة من اختبارات pgTAP عدد 11/11 في مشروع الاختبار، بما يشمل صلاحيات invoker، ونطاق مفاتيح التقدم، وحد المعدل. تحققنا من وجود مهمة تنظيف واحدة، وأن RPC ليست SECURITY DEFINER، وعدم بقاء بيانات مستخدم الاختبار أو أحداثه. أظهر Security Advisor عدم وجود تحذير SECURITY DEFINER لهذه الدالة؛ بقيت ملاحظات عامة تخص جداول اختبار أخرى وحماية كلمات المرور المسربة. لم يُنفذ اختبار HTTP runtime للوظيفة بعد، ولم تُشغّل Godot أو CI أو Gradle أو APK. مشروع الإنتاج لم يتغير.
