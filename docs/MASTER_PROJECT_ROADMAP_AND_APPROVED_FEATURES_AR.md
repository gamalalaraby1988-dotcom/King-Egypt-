# السجل الرئيسي لمشروع KING OF EGYPT CITY
## الأفكار المعتمدة، حالة التنفيذ، وترتيب مراحل الإنجاز

**الفرع المعتمد:** `feature/building-quick-travel`  
**الغرض:** مرجع مركزي واحد للقرارات المعتمدة وحالة تنفيذها، لتجنب إعادة مناقشة ما تم اعتماده أو اعتبار الواجهات الأولية أنظمة مكتملة.  
**قاعدة التحديث:** لا تتحول أي مهمة إلى «مكتملة» إلا بوجود تنفيذ فعلي ودليل اختبار مناسب. وجود ملف أو واجهة أو وثيقة تصميم لا يثبت اكتمال الوظيفة.

---

## 1. قواعد إدارة التنفيذ

1. العمل حصريًا على فرع `feature/building-quick-travel`، وعدم تعديل `main` أو الدمج إليه دون إذن صريح.
2. الحفاظ على الحسابات والملكية والتقدم والبيانات القديمة؛ أي ترحيل يتطلب جردًا ونسخة احتياطية ومصالحة واختبارات قبل اعتماد النتيجة.
3. عدم إنشاء شخصية مؤسس بديلة، وعدم منح صلاحيات المؤسس لحساب اختبار.
4. عدم طلب كلمات مرور أو رموز OTP أو مفاتيح سرية من المستخدم.
5. عدم تفعيل أسعار أو مكافآت أو مشتريات أو تغيير أرصدة قبل اكتمال الاقتصاد الموحد واختباره واعتماده صراحة.
6. لا يُدّعى نجاح اختبار Godot أو Android أو Realtime أو الخادم دون سجل أو دليل تشغيل.
7. الأصول النهائية ثلاثية الأبعاد والصوتية والفنية لا تُعد موجودة لمجرد وجود مشهد بديل أو شكل هندسي منشأ بالكود.
8. كل مرحلة لها مخرجات ومعايير قبول؛ لا يُعلن إغلاقها قبل تحقق المعايير.
9. عند وجود اعتماد خارجي حقيقي (مثل إنتاج موديلات 3D أو اختبار جهاز فعلي)، يوثق كحاجز واضح ولا يُخفى خلف علامة اكتمال.
10. لا تُعاد مناقشة القرارات المسجلة هنا إلا إذا طلب المستخدم تغييرها أو ظهر تعارض تقني يتطلب قرارًا جديدًا.

## 2. تعريف الحالات

- **مدمج برمجيًا:** يوجد تنفيذ في ملفات المشروع، لكن لا يعني بالضرورة أنه اختُبر أو اكتمل.
- **جزئي:** توجد بداية تنفيذ أو واجهة، مع وظائف أو تكاملات ناقصة.
- **معتمد تصميميًا:** القرار محفوظ، والتنفيذ لم يكتمل بعد.
- **متبقٍ:** لا يوجد دليل كافٍ على التنفيذ.
- **مكتمل ومختبر:** تحقق التنفيذ ومعايير القبول مع وجود دليل اختبار.
