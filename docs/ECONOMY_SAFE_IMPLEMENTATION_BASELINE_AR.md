# خط أساس تنفيذ الاقتصاد الآمن — KING OF EGYPT CITY

**الحالة:** جرد تنفيذي حديث وخطة مراحل على فرع مستقل؛ لا يمثل تنفيذًا لخدمة اقتصاد خادمية أو ترحيل بيانات.
**الفرع:** `feature/economy-safe-migration-mainline`
**الأساس:** `main` عند `003f82bb85c1d0865f1fdee4fa883ed317b4c991`
**الهدف:** الانتقال مستقبلًا من المحفظة المحلية إلى اقتصاد موثوق خادميًا، مع الحفاظ على كل أرصدة اللاعبين وملكياتهم وإيصالاتهم وتقدمهم.

## 1. القرارات الثابتة التي يجب ألا تتغير

- العملات ثلاث فقط: Cash (المال)، Chips (الرقائق)، Gems (الجواهر).
- XP تقدم وخبرة منفصلة، وليست عملة.
- لا تداول أو بيع أو شراء بين اللاعبين.
- لا اختراع أسعار أو مكافآت أو حدود غير معتمدة.
- لا تغيير في مدة الحفلة المعتمدة: 20 ثانية.
- لا تُفعّل واجهات أو أنظمة الأزياء القديمة؛ الشخصيات الجاهزة هي المعتمدة.
- لا حذف للمحفظة القديمة أو ملفات الحفظ أو إيصالاتها قبل نجاح الترحيل والتحقق والاسترجاع.
- لا نشر ترحيلات أو وظائف أو أسرار Supabase للإنتاج ضمن هذه المرحلة.
- لا دمج تلقائي إلى `main`.

## 3. المخاطر التي يجب حلها قبل نقل مصدر الحقيقة

### 3.1 ملف حفظ مشترك
المسار `user://kings_city_profile.cfg` يحتوي بيانات الملف الشخصي والاقتصاد والملكية والتقدم والإعدادات. المحفظة تستخدم حفظًا ذريًا ونسخة احتياطية، بينما `ProfileSettings` ينفذ `ConfigFile.save` مباشرة. يجب منع أي كتابة من نسخة قديمة من الملف من استبدال أرصدة أو ملكيات أحدث.

### 3.2 مصدران متوافقان للأرصدة
المحفظة تحتفظ بالأرصدة في `wallet.balances` وتتحقق من تطابق المال والرقائق مع `profile.money` و`profile.chips`. عند وجود اختلاف، تقفل عمليات العملة بدل التخمين. لا يجوز جمع القيم أو اختيار الأعلى أو الأقل أو استبدال إحداها تلقائيًا.

### 3.3 حد الرصيد
الكود الحالي يفرض `MAX_BALANCE = 2,000,000,000`. الهدف يدعم أرصدة كبيرة حتى نطاق التريليونات، لكن لا يُغيّر النوع أو السقف قبل اختبار دقة integer64 والتسلسل الشبكي والتخزين والعرض. لا تعتمد قيمة سقف اقتصادي جديدة في هذه المرحلة.

### 3.4 اعتماديات متعددة
`MissionManager` يمنح مكافآت ويحفظ التقدم، و`VehicleStoreManager` يشتري المركبات والألوان عبر المحفظة. لا يجوز حذف Autoload أو تغيير واجهات المحفظة قبل حصر كل المستدعين واختبارهم.

### 3.5 بيانات تاريخية لا يجوز إتلافها
تُحفظ نسخة من الأرصدة والإيصالات والسجل والتقدم وملكية المركبات والألوان وأي مفاتيح قديمة قبل أي تحويل. لا تُحذف ملفات الأزياء القديمة أو مفاتيحها في مشروع الاقتصاد؛ تُعزل عن التشغيل فقط وفق قرار الشخصيات الجاهزة، وتُترك بياناتها دون حذف حتى اعتماد سياسة أرشفة منفصلة.

## 4. مراحل التنفيذ وبوابات القبول

### المرحلة 0 — خط الأساس (هذه الوثيقة)
- تثبيت SHA المصدر وقائمة الملفات الحساسة.
- منع نقل PR #3 أو أي فرع متباعد ككتلة واحدة.
- لا تعديل بيانات أو قاعدة بيانات أو إعدادات إنتاج.

### المرحلة 1 — تقوية الحفظ المحلي واختباراته
- إنشاء اختبارات معزولة لملف حفظ اصطناعي، لا تستخدم ملف اللاعب الحقيقي.
- اختبار كتابة إعدادات الملف الشخصي بالتزامن مع حفظ المحفظة وشراء مركبة/لون.
- اختبار فشل القراءة والكتابة، واستعادة النسخة الاحتياطية، وتكرار الإيصال.
- فصل حفظ إعدادات العرض/الصوت/اللغة عن ملف الاقتصاد أو اعتماد تحديث جزئي آمن، دون تغيير هوية الحساب أو الأرصدة.
- لا تغيّر واجهة اللعب ولا الأسعار ولا المكافآت.
- بوابة القبول: لا كتابة قديمة تمحو تحديثًا أحدث، وكل اختبارات التراجع/الاستعادة ناجحة.

### المرحلة 2 — قارئ ترحيل للقراءة فقط
- بناء محلل يقرأ نسخة من ملف قديم دون تعديل المصدر.
- يستخرج الأرصدة الثلاثة وXP والإيصالات والسجل والملكيات والتقدم وإصدار المخطط.
- يقارن `wallet.balances` مع `profile.money/chips`، ويضع الحساب المتعارض في حالة مراجعة بدل اختيار قيمة.
- يحفظ بصمة المصدر وملخصًا قابلًا للمقارنة.
- بوابة القبول: لا فقد ولا زيادة ولا تعديل في ملف المصدر، ونتيجة التحليل قابلة للتكرار.

### المرحلة 3 — ترحيل تجريبي معزول
- لا يبدأ قبل مراجعة وثائق Supabase الحالية واختيار مخطط اختبار منفصل بوضوح.
- يستخدم حسابات اختبار اصطناعية فقط، مع RLS وصلاحيات محددة ومنع وصول مباشر غير لازم.
- يستخدم مفاتيح طلب فريدة، ومعاملات ذرية، وقيود منع تكرار.
- يعاد تشغيل الترحيل مرتين لإثبات idempotency.
- تقارن الأرصدة والملكيات والتقدم والإيصالات قبل وبعد.
- لا نشر إلى الإنتاج ولا لمس حسابات لاعبين حقيقيين.

### المرحلة 4 — طبقة خدمة موحدة في Godot
- تقديم واجهة واحدة لقراءة الحساب وطلب الشراء/المكافأة/الخصم.
- العميل يرسل نية الفعل ومعرف الطلب؛ الخادم يحدد السعر والاستحقاق والرصيد والملكية.
- الواجهة تعرض آخر رصيد معروف مع توضيح أنه غير محدث عند انقطاع الاتصال، وتعطل العمليات الاقتصادية حتى تأكيد الخادم.
- ترحيل `MissionManager` و`VehicleStoreManager` تدريجيًا عبر محولات صغيرة واختبارات، لا باستبدال شامل.
- إبقاء المحفظة القديمة للقراءة/الرجوع فقط إلى أن ينجح الانتقال.

### المرحلة 5 — إطلاق محدود ثم إزالة التوافق القديم
لا تبدأ إلا بموافقة مستقلة وبعد إثبات:
- نسخ احتياطية قابلة للاستعادة.
- تطابق كامل للأرصدة والملكيات والتقدم والإيصالات.
- عدم تكرار الشراء أو المكافأة تحت الطلبات المتزامنة.
- اختبارات Godot وCI واختبارات Android عند الحاجة.
- خطة رجوع مجرّبة ومراقبة للأخطاء.
بعدها فقط يُقترح تعطيل الكتابة القديمة ثم إزالة Autoload والحقول القديمة في تغيير منفصل.

## 6. ما لا تدّعيه هذه الوثيقة

هذه الوثيقة جرد وخطة تنفيذ فقط. لا تنشئ API أو جداول أو migrations، ولا تغيّر كود اللعبة أو إعدادات Supabase، ولا تنقل أي رصيد، ولا تثبت وجود اقتصاد خادمي عامل. كل مرحلة لاحقة تحتاج تغييرات واختبارات وأدلة منفصلة.
