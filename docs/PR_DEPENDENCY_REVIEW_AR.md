# مراجعة طلبات الدمج والاعتماديات — KING OF EGYPT CITY

تاريخ المراجعة: 2026-11-25
الفرع: `integration/safe-mainline-audit`
النطاق: قراءة metadata والفروق وملفات محددة لطلبات الدمج المفتوحة. لم يتم دمج أي طلب ولم تُعدّل ملفات التطبيق أو قواعد البيانات.

## 1. تسجيل الدخول بالبريد — PR #156

- العنوان: Make email and password the primary player sign-in.
- الحالة: مفتوح، غير Draft، والهدف المعلن `main`.
- الفرع المصدر: `staging/email-auth-session`.
- المقارنة مع `main`: المصدر متباعد؛ 4 commits للأمام و188 للخلف. لذلك لا يُعامل كفرع جاهز للدمج المباشر.
- التغيير الوظيفي يضيف تسجيل الدخول بالبريد وكلمة المرور، مع الإبقاء على Google كبديل، وإعادة استخدام مسار الجلسة الحالي.
- **مانع دمج مهم:** ملف `project.godot` في فرع PR يوجّه إعدادات العميل `founder/auth/api_base_url` و`publishable_key` إلى مشروع Supabase TEST (`unwrlvyjrtdwobcktetd)) بدل إعدادات الإنتاج الموجودة على `main`. لا يجوز دمج هذا الإعداد إلى خط إنتاج العميل كما هو.
- يلزم فصل إعدادات TEST عن إعدادات الإنتاج بطريقة صريحة وآمنة، ثم إعادة تأسيس التغيير على رأس حديث من `main` ومراجعة اختبارات الدخول واستعادة الجلسة على APK Android قبل الدمج.
- وصف PR نفسه يوضح أن الميزة لا تنشئ حسابات جديدة ولا تربط تلقائيًا حسابات Google القديمة بكلمة مرور. يجب إبقاء هذه الحدود واضحة في تجربة المستخدم.

## 2. خادم الجلسات وبيئة TEST — PR #151

- PR #151 مفتوح كمسودة، وقاعدته هي `feature/royal-jet-ski-championship` وليس `main`.
- يضيف متغيرات بيئة لتوجيه طلبات الخادم إلى Supabase TEST، ويصف متطلبات WSS/TLS وأسرار HMAC.
- هذا تغيير بنية خادم حساس، وهو جزء من سلسلة تغييرات متراكبة؛ لا يُراجع أو يُدمج منفردًا على أنه تغيير صغير مستقل.
- التوجيه عبر متغيرات البيئة مفيد لعزل TEST، لكن يجب التحقق من أن وضع الخادم يرفض إعدادات ناقصة أو مختلطة، وأن مفاتيح العميل العامة لا تُعامل كأسرار خادمية، وأن أسرار HMAC لا تدخل Git أو سجلات التشغيل.
- وثيقة PR تقر صراحة بأن وجود وظيفة الدليل لا ينشئ خادمًا مستضافًا ولا يثبت اتصال لاعبين حقيقيين.

## 3. سلسلة خادم المدينة والجت سكي — PRs #149، #151، #152، #153، #154، #155، #160

- PR #149 مسودة كبيرة (نحو 3,482 إضافة و83 حذفًا) وتحتوي نظام الجت سكي والسباق ومزامنة خادمية؛ نجاح اختبارات العقود لا يثبت بعد تشغيل سباق متعدد اللاعبين على خادم فعلي.
- PRs #151–#155 تشكل سلسلة إعداد/تغليف/اختبار خادم TEST، وبعضها يعتمد على قواعد أو فروع أخرى. يجب توثيق ترتيب الاعتماديات وإعادة توجيه القواعد إلى فرع تكامل موحد قبل التفكير في الدمج.
- PR #155 يختبر قبول اتصال WSS عبر TLS proxy، لكنه يصرح بأن الاختبار لا يصادق لاعبين حقيقيين ولا يقيس اللعب.
- PR #160 مسودة معاينات للمشهد الفعلي للجت سكي، ومتراكب على PR #159؛ يجب فحص artifact الصور الناتجة من المشهد الحقيقي قبل اعتماد شكل المجسم.

## 4. قرارات المراجعة الحالية

1. لا دمج لأي من الطلبات أعلاه إلى `main` في هذه المرحلة.
2. أولوية الإصلاح: فصل إعدادات Supabase TEST/PRODUCTION في PR #156، ثم توحيد سلسلة خادم TEST على فرع تكامل مستقل.
3. لا تُفعّل مزامنة اللاعبين أو الأصدقاء أو دليل الجلسات في الإنتاج قبل إثبات وجود الخدمات والسياسات اللازمة واختبارها.
4. لا يُعلن تعدد اللاعبين أو السباق جاهزًا قبل اختبار عميلين على الأقل على خادم WSS فعلي في TEST، ثم اختبار انقطاع الاتصال وإعادة الاتصال والتحقق الخادمي.
5. لا تُجرى أي تغييرات على Supabase PRODUCTION ضمن هذه المراجعة.

## حدود المراجعة

هذه مراجعة ساكنة لبيانات GitHub والفروق والملفات المحددة أعلاه. ليست مراجعة أمنية شاملة، ولا اختبار اختراق، ولا اختبار APK على جهاز فعلي، ولا تحققًا من تشغيل خادم عام. يجب مراجعة أحدث commits والـ CI والملفات المتغيرة مرة أخرى قبل أي قرار دمج.
