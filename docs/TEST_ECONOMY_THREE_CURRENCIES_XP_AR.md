# تقرير نموذج العملات الثلاث وXP — بيئة الاختبار

**التاريخ:** 13 نوفمبر 2026  
**المشروع:** `KING_OF_EGYPT_CITY_TEST`  
**المخطط:** `game_test` فقط  
**الفرع:** `supabase-free-test-environment`

## ما تم توسيعه

- `cash_balance` و`chips_balance` و`gems_balance`: ثلاثة أرصدة مستقلة من نوع `bigint` وغير سالبة.
- `account_progress.xp_total`: XP محفوظ في جدول تقدم مستقل، وليس في جدول العملات.
- `account_version`: رقم متزايد لكل تغيير في الحساب، بما في ذلك تغييرات XP.
- `ledger.asset_type` و`idempotency_requests.asset_type`: تمييز نوع الأصل الذي تتعلق به العملية.
- `apply_test_asset_delta`: دالة اختبار موحدة للعملات الثلاث وXP، مع قفل صف الحساب والتحقق من overflow ومنع التكرار.
- أبقينا `apply_test_delta` كغلاف توافق قديم يوجّه عمليات الاختبار القديمة إلى Cash فقط.

لا توجد واجهة عامة أو صلاحية تنفيذ للدالة من `anon` أو `authenticated` أو `service_role`. لا يستطيع تطبيق Godot استدعاء هذا النموذج مباشرة.

## نتائج الاختبار الاصطناعي

استخدم حساب اختبار واحدًا بقيم ابتدائية صفرية:

| الأصل | العملية | القيمة النهائية المتحققة |
|---|---:|---:|
| Cash | إضافة 100 | 100 |
| Chips | إضافة 200 | 200 |
| Gems | إضافة 300 | 300 |
| XP | إضافة 400 | 400 |

كانت `account_version = 4` بعد العمليات الأربع. يثبت ذلك أن الأرصدة الثلاثة لا تتداخل، وأن XP محفوظ منفصلًا.

### حالات الرفض وإعادة المحاولة

- إعادة طلب Cash نفسه بالمفتاح نفسه أعادت `replayed=true` دون إضافة ثانية.
- إعادة استخدام مفتاح Cash نفسه لطلب Chips رُفضت بتعارض مفتاح منع التكرار.
- خصم 201 Chips من رصيد 200 رُفض بسبب عدم كفاية الرصيد.
- محاولة تجاوز الحد الأعلى لـ `bigint` في Gems رُفضت بسبب overflow.
- لم يُنشأ سجل idempotency لعملية الخصم الفاشلة.
- غلاف الدالة القديمة أضاف 5 إلى Cash فقط، ولم يمس Chips أو Gems أو XP.

بعد هذه العمليات كانت القيم:
- Cash: 105
- Chips: 200
- Gems: 300
- XP: 400
- account_version: 5

عدد سجلات ledger وطلبات idempotency كان 5، وكلها مرتبطة بالعمليات الناجحة فقط.

### مراجعة إدخال نوع الأصل

أُضيف تحقق صريح لرفض `asset_type = NULL`، لأن SQL يستخدم منطقًا ثلاثي القيم وقد يمرر قيمة فارغة دون شرط `IS NULL` صريح. الاختبار أعاد رفضًا واضحًا، وتأكدنا من عدم إنشاء أي سجل idempotency جزئي.

بعد اكتمال الفحص حُذف حساب الاختبار الاصطناعي وسجلاته. تحققنا أن الجداول الأربعة فارغة:
- wallets: 0
- ledger: 0
- idempotency_requests: 0

## مراجعة الوصول

تم التحقق أن مخطط `game_test` لا يمنح `USAGE` إلى `anon` أو `authenticated` أو `service_role`، وأن هذه الأدوار لا تملك صلاحية تنفيذ الدالة الجديدة. RLS مفعّل على الجداول الأربعة ولا توجد سياسات؛ وهذا متعمد حاليًا لأن النموذج غير مكشوف لأي عميل.

مراجعة الأداء بعد الترحيل لم تُظهر تنبيهات.

## الحدود وما لم يُعتمد بعد

هذا نموذج قاعدة بيانات تجريبي، وليس اقتصاد اللعبة النهائي أو API إنتاجيًا. لم يُنفذ بعد:
- مصادقة اللاعبين وربط `player_id` ثابت بجلسة موثوقة.
- واجهة Edge Function أو RPC آمنة مخصصة للعبة.
- كتالوج أسعار أو عمليات شراء أو مكافآت حقيقية.
- اختبار تزامن مستقل باتصالات PostgreSQL متعددة.
- اختبار انقطاع الشبكة بعد COMMIT أو اختبار ضغط.
- ربط Godot أو ترحيل ملفات الحفظ المحلية.

لم تتغير أي بيانات لاعب حقيقية أو أرصدة حية، ولم تُغيّر أسعار أو حدود اقتصادية. XP لا يزال منفصلًا ولا يمثل عملة رابعة.
