# تصميم نموذج ملف اللاعب الخادمي — المرحلة B (تصميم فقط)

المشروع: KING OF EGYPT CITY  
الفرع: `feature/building-quick-travel`  
النطاق: تصميم عقد ملف اللاعب الخادمي وربطه بهوية المصادقة والشخصية الجاهزة والتقدم.  
الحالة: مقترح هندسي موثق؛ لا SQL ولا migrations ولا تعديل قاعدة بيانات أو كود في هذه المرحلة.

## 1) القرار المعماري الأساسي

**هوية الحساب هي مفتاح الوصول، وليست قيمة يختارها العميل.**

التسلسل:

`جلسة Supabase موثقة (auth.uid()) → game_test.auth_account_links → test_account_id ثابت → ملف اللاعب وملف التقدم`

- لا يرسل العميل `auth_user_id` أو `test_account_id` لاختيار سجل لاعب عند القراءة أو الكتابة.
- كل RPC تستخرج هوية المستخدم من `auth.uid()` ثم تحل الربط بنفسها.
- `player_code` رمز عام للبحث الاجتماعي فقط، ولا يستخدم لإثبات الملكية أو المصادقة.
- قيد فريد على `auth_account_links.auth_user_id` يضمن حساب لاعب واحد لكل Auth UID، وقيد فريد على `test_account_id` يمنع ربط سجل لاعب بأكثر من حساب.
- تبقى آلية السماح بتهيئة حساب الاختبار كما هي؛ لا توسيع allowlist ولا إنشاء حسابات جديدة تلقائيًا.
- هذا التصميم خاص ببيئة الاختبار الحالية `game_test`. لا يفترض أن هذه الجداول أو آلية allowlist هي تصميم الإنتاج النهائي.

## 2) ما هو موجود بالفعل وفق ملفات المشروع

المراجعة الساكنة لملفات migrations الموجودة على الفرع أظهرت:

| الكيان | دوره الحالي الظاهر في المصدر |
|---|---|
| `game_test.auth_account_links` | ربط Auth UID بمعرف حساب اختبار |
| `game_test.player_identities` | هوية اللاعب ورمز اللاعب العام |
| `game_test.player_profiles` | ملف يحتوي الاسم العام وتاريخ تغييره، ويُنشأ أثناء التهيئة |
| `game_test.account_progress` | تقدم XP المستخدم في مطالبة الصندوق |
| `game_test.wallets` | أرصدة اختبار؛ خارج نطاق هذا التصميم ولا تُعدل |
| `game_test.ledger` | دفتر مالي تجريبي؛ خارج نطاق هذا التصميم ولا يُعدل |

ملاحظة: هذه أسماء وحقول مستخدمة في migrations التي تمت مراجعتها، وليست تدقيقًا مباشرًا للحالة الحالية لقاعدة البيانات. لا يُفترض وجود أعمدة غير ظاهرة في ملفات المشروع.

## 3) نموذج البيانات المنطقي المقترح

بدل إنشاء جدول مكرر باسم player profile، يكون ملف اللاعب **عقدًا منطقيًا واحدًا** يجمع بيانات من جداول متخصصة موجودة، مع إضافة حقول محدودة عند اعتماد التنفيذ.

### 3.1 هوية اللاعب

المصدر: `game_test.auth_account_links` و`game_test.player_identities`.

- Auth UID: داخلي، لا يُعرض للاعب ولا يقبله العميل كمعامل ملكية.
- Test Account ID: معرف داخلي ثابت.
- Player Code: رمز عام ثابت وفريد للبحث الاجتماعي.
- Created At: وقت الإنشاء الخادمي.
- لا يسمح بتبديل الربط من Auth UID إلى حساب آخر عبر RPC العميل.
- لا يعاد إنشاء هوية عند إعادة تثبيت اللعبة أو تبديل الجهاز.

### 3.2 ملف اللاعب العام

المصدر الحالي المقترح: توسيع `game_test.player_profiles` بدل إنشاء جدول ثانٍ للاسم.

| الحقل المقترح | النوع المنطقي | الغرض | سلطة التعديل |
|---|---|---|---|
| `test_account_id` | UUID | مفتاح الملف، مرتبط بسجل الهوية | الخادم |
| `display_name` | نص 1–24 حرفًا | اسم العرض الحالي | RPC الاسم المعتمدة فقط |
| `last_name_change_at` | timestamptz | وقت آخر تغيير اسم | الخادم فقط |
| `selected_character_id` | نص قصير ثابت | معرف إحدى الشخصيات الـ16 | RPC اختيار شخصية بعد التحقق |
| `profile_version` | bigint موجب | نسخة الملف لمنع الكتابة القديمة | الخادم فقط |
| `created_at` | timestamptz | وقت إنشاء الملف | الخادم فقط |
| `updated_at` | timestamptz | آخر تحديث | الخادم فقط |

ملاحظات:
- `selected_character_id` لا يضاف قبل اعتماد قائمة IDs وربط كل ID بأصل نهائي موجود.
- لا يخزن هذا الملف الاسم المحلي القديم ولا إعدادات الجهاز ولا الأرصدة.
- لا يسمح بتحديث الصف كاملًا من العميل؛ كل مجال له RPC محدود.
- لا تستخدم `user_metadata` أو بيانات يرسلها العميل لتحديد صلاحية الحساب أو مالكه.

### 3.3 تقدم اللاعب

المصدر الحالي الظاهر: `game_test.account_progress` لحقل XP، مع حاجة تصميمية لتوسيع نموذج التقدم بعد جرد بقية مصادره.

الحقول المنطقية:
- `test_account_id`: ربط ثابت بهوية اللاعب.
- `xp_total`: XP صحيح غير سالب؛ XP تقدم وليس عملة.
- `progress_version`: رقم نسخة خادمي.
- `updated_at`: وقت التحديث الخادمي.

المهام والوظائف والإنجازات والأنشطة اليومية لا تُحشر في JSON قابل للكتابة الحرة. بعد جرد مخططها الحالي، تحفظ كسجلات/أحداث خادمية منظمة بمعرفات ثابتة ومفاتيح idempotency، وتقدم واجهة الملف ملخصًا محسوبًا منها. لا ننشئ الآن جداول إضافية قبل تحديد مصدر الحقيقة لكل نوع وتعارضات الحقول القديمة.

## 4) قائمة الشخصيات الجاهزة

قائمة مرجعية ثابتة من 16 معرفًا، 8 رجال و8 نساء، يجب اعتمادها وربطها بالأصول النهائية قبل تنفيذ اختيار الشخصية.

قواعد:
1. كل ID فريد وثابت ولا يعاد استخدامه لشخصية أخرى.
2. العميل يعرض فقط الشخصيات المسموح بها من كتالوج ثابت/معتمد.
3. الخادم يتحقق من ID ضمن القائمة المعتمدة، ولا يقبل اسم ملف أو مسار asset يرسله العميل.
4. لا توجد حقول outfit أو hairstyle أو wardrobe في نموذج الاختيار الجديد.
5. لا يُستبدل اختيار لاعب قائم بصمت عند تحديث قائمة الأصول؛ تُدار حالات التقاعد/الاستبدال بخطة توافق واضحة.
6. عند غياب الاختيار لحساب جديد فقط، يمكن اعتماد default character ID بعد تحديده صراحة. لا يطبق default فوق اختيار محفوظ موجود.

**حالة القائمة الآن:** لم تظهر في الملفات التي تمت مراجعتها قائمة معرفات معتمدة للشخصيات الـ16 أو أصول نهائية قابلة للربط؛ لذلك تبقى IDs غير محددة ولا نخترعها.

## 5) عقد API / RPC المقترح

كل RPC يستنتج الحساب من الجلسة ولا يقبل Auth UID أو test account ID من العميل.

| العملية | الغرض | مدخلات العميل | ما يجب أن يفعله الخادم |
|---|---|---|---|
| `get_my_test_player_profile` | تحميل ملف اللاعب | لا شيء | حل Auth UID ثم إعادة الملف والهوية والنسخ |
| `set_my_test_selected_character` | حفظ الشخصية الجاهزة | character ID فقط + expected profile version | تحقق من القائمة، قفل/تحديث ذري، زيادة النسخة |
| `get_my_test_player_progress` | تحميل التقدم | لا شيء | إعادة XP والملخصات الخادمية المسموح بها |
| `get_my_test_player_bootstrap` | تهيئة دخول واحدة | لا شيء | إرجاع الهوية والملف والتقدم في snapshot متسق |
| `get_my_test_display_name` | الاسم | لا شيء | الإبقاء على المسار الحالي، مع دمجه في عقد التحميل لاحقًا دون كسر العميل |
| `change_my_test_display_name` | تغيير الاسم اليومي | الاسم الجديد فقط | الإبقاء على تحقق الحد اليومي بتوقيت القاهرة |

ملاحظات:
- أسماء RPC أعلاه مقترحة وليست موجودة أو منشورة حاليًا إلا ما هو موثق في المigrations.
- يجب ألا يؤدي طلب bootstrap إلى إنشاء لاعب جديد أو تعديل الملف ضمنيًا. إنشاء/تهيئة الحساب يظل مسارًا منفصلًا ومصرحًا.
- لا يُعاد إلى العميل Auth UID أو أي سر جلسة ضمن ملف اللاعب.
- تُعاد أخطاء مميزة: `authentication_required`, `test_account_not_linked`, `profile_not_ready`, `invalid_character_id`, `version_conflict`, `temporarily_unavailable`.

## 6) سياسة النسخ والتعارض

- كل تحديث لملف اللاعب يحمل `expected_profile_version`.
- الخادم يقارن النسخة المتوقعة بالنسخة الحالية تحت قفل صف داخل معاملة.
- إذا اختلفتا، يرفض الكتابة بـ `version_conflict` ويعيد النسخة الحالية/ملخصًا آمنًا لإعادة التحميل.
- لا يستخدم توقيت الجهاز لحسم الأحدث.
- لا يُسمح لعميل قديم بإرسال snapshot كامل واستبدال حقول لا يملك صلاحية تعديلها.
- لا تستخدم last-write-wins على الملف كاملًا.
- يمكن تقسيم النسخ لاحقًا لكل نطاق (profile/progress) إذا أثبتت الاختبارات الحاجة، مع إبقاء كل نطاق خادميًا.

## 7) أمن قاعدة البيانات

التنفيذ المستقبلي يجب أن يحقق جميع الآتي:
- RLS مفعّل على كل جدول مكشوف، ويفضل إبقاء جداول اللعبة في schema غير مكشوفة للعميل.
- لا صلاحية مباشرة للعميل على جداول الهوية والملف والتقدم؛ يقتصر الوصول على RPC محددة.
- أي دالة ذات صلاحيات مرتفعة يجب أن تكون في schema غير مكشوف، مع فحص `auth.uid()` داخلها، و`search_path` مضبوطًا، وسحب EXECUTE من PUBLIC وanon ومنح الحد الأدنى فقط.
- لا تعتبر `TO authenticated` وحدها تفويضًا؛ يجب حل ملكية الحساب من الجلسة والتحقق منها.
- لا تستخدم `SECURITY DEFINER` لمجرد تجاوز خطأ صلاحيات؛ إن كانت لازمة فيجب مراجعة نطاقها وتبعياتها واختبارها.
- لا تعتمد على `user_metadata` لتحديد ملكية أو صلاحية.
- لا تسجل رموز الدخول أو OTP أو Authorization headers.
- لا تضع مفاتيح service_role أو مفاتيح سرية في Godot أو المستودع.
- لا تمنح حساب الاختبار أو المؤسس دورًا إداريًا بسبب اسمه أو player_code.

## 8) ترتيب التحميل عند دخول المدينة

1. مصادقة ناجحة وجلسة صالحة.
2. حل ربط Auth UID بسجل حساب الاختبار المصرح به.
3. طلب bootstrap للملف والتقدم.
4. التحقق من شكل الاستجابة وإصداراتها ووجود الشخصية ضمن القائمة.
5. تحميل الأصل الجاهز المطابق.
6. تحميل بيانات اللعب غير المالية المسموح بها.
7. بعد اكتمال التحميل فقط، تتحول الواجهة إلى حالة اللاعب داخل المدينة.

إذا فشل أي طلب:
- لا تُنشأ هوية بديلة.
- لا تُحمّل تقدمًا محليًا من حساب سابق.
- لا يُحفظ ملف افتراضي فوق الملف الخادمي.
- تظهر حالة اتصال/إعادة محاولة واضحة، مع خيار إعادة تسجيل الدخول عند انتهاء الجلسة.

## 9) الفصل عن المجالات الأخرى

- إعدادات الصوت والجودة واللغة والتحكم تبقى في ملف محلي مستقل لكل جهاز.
- الاقتصاد والمحفظة والدفتر والمشتريات لا تدخل في هذا التغيير؛ لا تعديل أو ترحيل أو تفعيل.
- بيانات الشقة تبقى خارج ملف اللاعب العام، وتحتاج لاحقًا إلى نموذج شقة ومالك وصلاحيات ضيف.
- بيانات المحادثات والأصدقاء تبقى في نطاقها الاجتماعي الحالي.
- الخزانة والأزياء القديمة لا تدخل النموذج.
- لا تخزن refresh token أو access token في ملف اللاعب.

## 10) خطة الاختبار قبل التنفيذ الإنتاجي

| الاختبار | القبول |
|---|---|
| حساب اختبار واحد يعيد bootstrap عدة مرات | نفس test_account_id وplayer_code وملف اللاعب |
| حسابان مختلفان | لا قراءة أو كتابة متقاطعة |
| تمرير معرف حساب آخر كمدخل | لا توجد معاملات ملكية تقبل هذا المعرف |
| اختيار ID غير موجود | رفض خادمي |
| اختيار شخصية صحيحة | نسخة الملف تزيد مرة واحدة وتظهر الشخصية بعد إعادة الدخول |
| طلبان متزامنان بنفس النسخة | نجاح تحديث واحد ورفض الآخر كتعارض |
| انقطاع الاتصال بعد حفظ الخادم | إعادة المحاولة لا تنشئ تغييرًا مكررًا |
| تبديل الحساب على الجهاز | مسح snapshot السابق قبل تحميل الجديد |
| انتهاء الجلسة | لا يتم تحميل ملف حساب قديم ولا استخدامه |
| فشل bootstrap | لا دخول كامل للمدينة ولا كتابة افتراضية |
| حساب المؤسس | لا اختبار أو تعديل أو ربط بديل دون موافقة منفصلة |

## 11) عناصر تحتاج قرارًا/مادة قبل التنفيذ

1. اعتماد قائمة معرفات الشخصيات الـ16 وربطها بالأصول النهائية.
2. تحديد ما إذا كان ملف التقدم سيبقى في `account_progress` مع جداول أحداث منفصلة، أو يحتاج توحيدًا منطقيًا عبر RPC فقط.
3. مراجعة تعريفات الجداول الفعلية وقيودها وRLS في قاعدة الاختبار قبل كتابة أي migration؛ ملفات migrations وحدها لا تثبت الحالة الفعلية الحالية.
4. تحديد سياسة ترحيل XP والمهام والإنجازات اليومية بعد مقارنة مصادرها المحلية المكررة.
5. مراجعة تخزين Android الآمن للجلسة في مرحلة مستقلة.

## 12) بوابة الاعتماد

هذا المستند **تصميم فقط**. لا ينشئ جداول ولا أعمدة ولا RPC ولا سياسات RLS، ولا يغير قاعدة البيانات أو كود اللعبة أو حسابات اللاعبين. لا يغير هوية المؤسس أو بياناته أو صلاحياته، ولا يوسع allowlist، ولا يفعّل أي جانب مالي.

قبل أي تنفيذ يلزم اعتماد هذا النموذج، وتوفير/اعتماد معرفات الشخصيات الـ16 وأصولها، ثم مراجعة الحالة الفعلية لقاعدة الاختبار ومخططها. تظل كل البيانات المالية خارج النطاق حتى اكتمال الاقتصاد الموحد ومراجعته واعتماده صراحة.
