# مراجعة التنفيذ الفني لفصل بيئات البناء

**التاريخ:** 2026-11-25  
**الفرع:** `feature/build-environment-separation-review`  
**الحالة:** مراجعة فنية آمنة قبل تعديل ملفات التشغيل؛ لا تغييرات تشغيلية أو على Supabase.

## 1) الحالة التي أُعيد التحقق منها

- فرع التدقيق `integration/safe-mainline-audit` ما زال عند commit `5cd75d9eef5358c23ea218705ac905372fc0d503`.
- ملف `project.godot` في هذا الأساس يحدد إعدادات اتصال Supabase ضمن مجموعة `founder/auth/*` لبيئة PRODUCTION.
- `scripts/founder_auth_client.gd` و`scripts/player_account_auth_client.gd` يقرآن الإعدادات نفسها من ProjectSettings؛ لذلك يجب أن يظل مصدر الإعداد واحدًا ومبكر التحميل قبل بدء طلبات المصادقة.
- `export_presets.cfg` يحتوي preset واحدًا باسم `Android`، ويخرج APK باسم debug. لا يوجد حاليًا preset مستقل للاختبار وآخر للإنتاج.
- سير عمل `.github/workflows/android-debug-apk.yml` يبني APK debug فقط عند تشغيل workflow يدويًا، ويستخدم توقيع Android debug مؤقتًا.
- PR #156 ما زال مفتوحًا وغير مدمج، ويغيّر إعداد الاتصال في نسخته إلى TEST داخل `project.godot`. يجب عدم نقل هذا التغيير إلى إعداد الإنتاج كما هو.

## 2) نقطة تصميم حاسمة قبل التنفيذ

لا يكفي إنشاء ملفي إعداد فقط؛ يجب ضمان اختيار البيئة في مرحلة البناء، قبل أن تبدأ Autoloads الخاصة بالمصادقة، ومنع تشغيل إصدار الإنتاج بإعداد TEST أو العكس.

التصميم المقترح للتنفيذ على هذا الفرع:

1. إضافة Autoload صغير لإعداد بيئة البناء، يحمّل ملف الإعداد المختار قبل Autoloads المصادقة.
2. إضافة ملفي إعداد غير سريين منفصلين: TEST وPRODUCTION، يحتوي كل منهما اسم البيئة وعنوان المشروع ومفتاح publishable الخاص به وURI التحويل.
3. جعل اختيار البيئة صريحًا بعلامة بناء مخصصة، مع رفض حالة وجود العلامتين معًا. في غياب علامة التصدير، يبقى تشغيل المحرر على إعداد المشروع الافتراضي الحالي حتى لا تتعطل جلسات التطوير دون قصد.
4. إنشاء مسارين منفصلين للتصدير: Android TEST-debug وAndroid PRODUCTION-release. لا يُنشأ توقيع إنتاجي أو تُخزّن مفاتيحه في المستودع.
5. إضافة بوابة CI تفحص توافق علامة البناء وملف الإعداد وعنوان Supabase قبل التصدير، وتفشل عند أي تعارض.
6. إضافة اختبارات عقدية تؤكد أن عميل المصادقة وخدمة استحقاق المؤسس يقرآن الإعداد الموحد نفسه.

## 3) ضوابط أمنية

- مفتاح publishable ليس مفتاح service-role، ومع ذلك يجب ألا يختلط مفتاح TEST بعنوان PRODUCTION.
- يمنع تضمين service-role أو مفاتيح توقيع خاصة أو مفاتيح توقيع تذاكر المؤسس في ملفات اللعبة أو Git.
- لا يعتمد اختيار البيئة على اسم اللاعب أو قيمة يرسلها العميل.
- لا يتغير حساب المؤسس أو معرّفه الثابت أو صلاحياته في هذه المرحلة.
- لا يتم نشر Edge Function أو تعديل Auth أو قاعدة البيانات في أي مشروع Supabase خلال فصل بيئات البناء.

## 4) سبب عدم تعديل ملفات التشغيل في هذه المراجعة

المراجعة الحالية أعادت تأكيد أن إعداد البيئة مرتبط مباشرة بمرحلة بدء Autoloads، وأن مسار Android الحالي debug فقط. تنفيذ تغيير تشغيلي دون تشغيل Godot 4.7.2 headless واختبار تصدير Android فعلي سيترك احتمالًا غير مقبول لبدء المصادقة قبل تحميل البيئة أو لتصدير APK متصل بالمشروع الخطأ.

لذلك فُصلت هذه المراجعة في فرع مستقل بدل إجراء تعديل غير قابل للتحقق. الخطوة التالية هي تنفيذ التغييرات أعلاه على هذا الفرع، ثم تشغيل فحوص Godot وCI؛ ولا يُعتبر الفصل مكتملًا قبل نجاح بوابات TEST وPRODUCTION.

## 5) وضع الأنظمة بعد المراجعة

- لم تتغير `main`.
- لم يتغير `integration/safe-mainline-audit`.
- لم يتم تعديل `project.godot` أو `export_presets.cfg` أو ملفات CI.
- لم يتم تعديل PR #156 أو دمجه.
- لم يتم تنفيذ SQL أو تغيير إعدادات Auth أو نشر وظائف على TEST أو PRODUCTION.
