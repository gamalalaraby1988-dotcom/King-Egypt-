# المعمارية التقنية للنظام المالي والاقتصادي الموحد
## KING OF EGYPT CITY

**الحالة:** تصميم تقني مقترح مبني على العقد المعتمد وجرد E0؛ ليس تنفيذًا أو اعتمادًا نهائيًا للمخطط.
**الفرع:** `feature/building-quick-travel`
**النطاق:** Cash وChips وGems والمشتريات والاستحقاقات والملكية، مع إبقاء XP منفصلة.
**قيد أساسي:** هذه الوثيقة لا تفعّل أي صرف أو شراء، ولا تغيّر أسعارًا أو مكافآت أو أرصدة.

## 1. المبادئ المعمارية

1. Postgres هو مصدر الحقيقة للأرصدة والدفتر والاستحقاقات والملكية.
2. كل طلب اقتصادي يمر عبر Economy Service خادمية واحدة، ولا يكتب عميل Godot إلى جداول الاقتصاد مباشرة.
3. تحديث الرصيد والدفتر والإيصال والاستحقاق والملكية ذات الصلة يتم في معاملة قاعدة بيانات واحدة.
4. كل طلب له مفتاح idempotency ثابت، ويُرفض استعمال المفتاح نفسه لطلب مختلف.
5. لا يرسل العميل مبلغًا أو عملة أو سعرًا أو مكافأة أو هوية مالك؛ يرسل نوع العملية ومعرف المنتج/النشاط ومفتاح الطلب فقط.
6. لا رصيد محلي قابل للصرف أو منح offline. بيانات العميل cache للعرض فقط.
7. Cash وChips وGems هي العملات الوحيدة. XP نظام تقدم منفصل.
8. لا تداول بين اللاعبين ولا تحويل عملة إلى عملة.
9. لا تفعيل مالي قبل اختبار النظام واعتماد تشغيله صراحة.

## 2. حدود المكونات

```text
Godot Client
  ├─ EconomyClient (طلب/عرض/إعادة استعلام)
  └─ UI: Wallet / Store / Rewards / Profile
              │ Auth JWT + Publishable key
              ▼
Supabase Data API / RPC
              │
              ▼
Private Economy Schema (Postgres)
  ├─ Identity mapping
  ├─ Economy Service functions
  ├─ Wallet balances
  ├─ Immutable ledger + idempotency
  ├─ Catalog + price rules
  ├─ Entitlements
  ├─ Ownership registry
  ├─ XP / progression (separate)
  └─ Audit + reconciliation
```

- يظل Supabase Auth مسؤولًا عن إثبات الجلسة. تربط الخدمة `auth.uid()` بحساب اللاعب الداخلي عبر ربط موثوق قائم، ولا تقبل account_id أو player_id من العميل كهوية صاحب العملية.
- لا يوضع service-role أو secret key في Godot أو APK.
- لا تُنشر جداول الاقتصاد في schema مكشوفة. يوصى بوضعها في schema خاص غير مكشوف عبر Data API.
- أي RPC عامة تكون واجهة ضيقة فقط، وتُمنح EXECUTE إلى `authenticated` فقط عند الحاجة. تُسحب صلاحيات PUBLIC وanon صراحة.
- يفضّل SECURITY INVOKER حيث يحقق التصميم أقل الصلاحيات. إذا ثبتت ضرورة SECURITY DEFINER لتجميع المعاملة أو الوصول الداخلي، فتكون الدالة داخل schema خاص، مع تحقق داخلي من `auth.uid()`، و`search_path` ثابت وآمن، ومراجعة ملكية الدالة وEXECUTE بعد الإنشاء. لا تُستخدم SECURITY DEFINER كحل عام لمشكلات الصلاحيات.

## 3. نموذج البيانات المنطقي المقترح

الأسماء أدناه أسماء تصميمية مقترحة وليست أسماء جداول منفذة. يجب فحص المخطط الحالي وتجنب التكرار قبل كتابة أي migration.

| الكيان المقترح | أهم الحقول | الغرض والقيود |
|---|---|---|
| `economy_wallets` | account_id PK/FK، cash_balance BIGINT، chips_balance BIGINT، gems_balance BIGINT، version BIGINT، updated_at | صف محفظة واحد لكل حساب؛ قيود عدم السالب؛ لا XP هنا |
| `economy_ledger` | ledger_id، account_id، request_id، asset، direction، amount BIGINT، balance_after BIGINT، event_type، source_id، reference_id، created_at | دفتر append-only؛ amount موجب مع direction منفصل؛ UNIQUE مناسب لمنع حركة مكررة |
| `economy_requests` | account_id، request_id، request_hash، operation، status، result_json، created_at، completed_at | سجل idempotency؛ UNIQUE(account_id, request_id)؛ نفس المفتاح ونفس الطلب يعيدان النتيجة السابقة، واختلاف المحتوى يرفض |
| `economy_catalog` | product_id، category، asset، price BIGINT، active، availability، catalog_version، eligibility_rule، metadata | كتالوج خادمي؛ لا أسعار موثوقة في العميل؛ لا تفعيل منتج أو سعر غير معتمد |
| `economy_entitlements` | entitlement_id، account_id، source_type، source_id، reference_key، status، reward_config_version، claimed_at | استحقاق فريد؛ قيد UNIQUE على الحساب ومفتاح المصدر/المرجع |
| `player_ownership` | ownership_id، account_id، item_type، item_id، source_ledger_id، acquired_at، state | ملكية خادمية؛ قيد فريد للحيازة المفردة حسب نوع/معرف العنصر |
| `economy_source_rules` | source_id، source_type، active، rule_version، limits، config | مصادر الإصدار والاستهلاك المعتمدة؛ تظل غير مفعلة افتراضيًا |
| `economy_audit` | audit_id، actor_type، actor_id، action، target_account_id، reason، reference_id، created_at | تدقيق إداري وأمني append-only، دون أسرار |
| `player_progression` / `progression_events` | account_id، xp_total BIGINT، level، event_id، source_reference، created_at | XP والتقدم منفصلان عن العملات، ويمكن ربطهما بمرجع الاستحقاق نفسه |

### علاقات رئيسية

- `economy_wallets.account_id` و`economy_ledger.account_id` و`economy_requests.account_id` و`economy_entitlements.account_id` و`player_ownership.account_id` تشير إلى هوية حساب اللعبة الثابتة، لا اسم العرض.
- `economy_ledger.request_id` يشير إلى الطلب الذي أنشأ الحركة.
- `player_ownership.source_ledger_id` يربط الملكية بحركة الشراء التي منحتها، أو بمرجع استحقاق مجاني موثق عند عدم وجود خصم.
- `economy_entitlements` تسجل أهلية النشاط مرة واحدة، بينما `economy_ledger` يسجل حركة العملة فقط عند استحقاق عملة. لا تتحول كل حالة إنجاز إلى حركة مالية تلقائيًا.
- لا تخزن قيم XP داخل حقول العملات أو دفتر العملات.

## 4. قواعد الدقة العددية

- تخزين الحسابات في PostgreSQL باستخدام BIGINT للأعداد الصحيحة الموقعة.
- جميع العمليات والحسابات في Godot تستخدم integer 64-bit دون float.
- لأن أعداد JavaScript/JSON الرقمية لا تضمن دقة كل قيم 64-bit، تُرسل الأرصدة والمبالغ الكبيرة عبر حدود JSON كسلاسل عشرية canonical، وتتحقق طبقة العميل من الصيغة والنطاق قبل تحويلها إلى int64.
- لا تعتمد قيمة BIGINT القصوى سقفًا اقتصاديًا. السقف الاقتصادي يظل غير محدد حتى مراجعة التضخم ومصادر الإنتاج والاستهلاك واعتماده.
- يمنع التقريب والقص والالتفاف overflow؛ أي تجاوز يُرفض قبل الكتابة.

## 5. بروتوكول تنفيذ الحركة الذرية

التنفيذ المقترح داخل دالة خادمية واحدة ومعاملة Postgres واحدة:

1. تحقق من جلسة المستخدم، ثم استخرج account_id من ربط الهوية الخادمي.
2. تحقق من operation وrequest_id وصيغة المدخلات، واحسب request_hash على المدخلات المسموح بها.
3. أنشئ سجل الطلب أو اقرأ السجل الموجود تحت قيد UNIQUE(account_id, request_id). إذا وجد:
   - نفس request_hash ونتيجة نهائية: أعد النتيجة السابقة دون أي أثر جديد.
   - request_hash مختلف: ارفض إعادة استخدام المفتاح.
   - طلب قيد التنفيذ: امنع التنفيذ الموازي أو أعد حالة pending بطريقة محددة.
4. اقفل صف المحفظة للحساب بقفل صف مناسب داخل المعاملة، وتحقق من version والرصيد.
5. اقرأ السعر/العملة/قواعد الأهلية من كتالوج وقواعد خادمية نشطة، لا من بيانات العميل.
6. تحقق من التوافر والحدود والملكية السابقة والاستحقاق ومنع الحظر/الأهلية حيث ينطبق.
7. نفذ تحديث الرصيد مع شرط عدم السالب وعدم overflow.
8. أضف حركة ledger غير قابلة للتعديل، واربطها بالطلب.
9. أنشئ الملكية أو الاستحقاق أو حدث XP المرتبط داخل المعاملة نفسها.
10. خزّن نتيجة الطلب النهائية والنسخة الجديدة للمحفظة، ثم commit.
11. عند أي خطأ قبل commit، تتراجع كل تغييرات المعاملة معًا؛ لا يبقى خصم بلا ملكية أو مكافأة بلا إيصال.
12. عند انقطاع العميل بعد نجاح الخادم، يستعلم عن الطلب بنفس request_id؛ لا ينشئ معرفًا جديدًا لإعادة العملية.

لا يُنفذ هذا البروتوكول عبر عدة RPC مستقلة للخصم ثم الملكية؛ حدود الذرية يجب أن تكون داخل الخادم نفسه.

## 6. عقود واجهات RPC المقترحة

واجهات تصميمية فقط؛ الأسماء والتواقيع النهائية تخضع لمراجعة الكود الحالي قبل التنفيذ.

| الواجهة | مدخلات العميل المسموحة | النتيجة |
|---|---|---|
| `get_my_economy_snapshot()` | لا شيء يحدد المالك | الأرصدة كسلاسل عشرية، version، وقت التحديث |
| `get_my_economy_history(cursor, limit)` | cursor وlimit محدودان | حركات الحساب الحالي فقط |
| `purchase_my_catalog_item(product_id, request_id)` | معرف منتج + مفتاح طلب | نتيجة شراء، حركة، ملكية، snapshot |
| `claim_my_entitlement(source_id, reference_key, request_id)` | معرف مصدر ومرجع نشاط + مفتاح طلب | حالة أهلية/مطالبة، المكافأة التي قررها الخادم، نتيجة ثابتة |
| `get_my_entitlement_status(source_id, reference_key)` | مرجع النشاط | الحالة الحالية للحساب المصادق |
| `get_my_ownership(item_type)` | مرشح نوع اختياري | قائمة ملكيات اللاعب فقط |
| `get_my_request_result(request_id)` | معرف طلب | النتيجة المحفوظة لطلب المستخدم نفسه |

- لا توجد واجهة عامة من العميل مثل `credit(amount)` أو `set_balance(value)` أو `purchase(price, currency)`.
- لا تقبل واجهة المكافأة قيمة cash/chips/xp من العميل.
- لا تعرض واجهة التاريخ بيانات لاعب آخر أو حقول تدقيق إدارية.
- لا تنفذ واجهات Admin أو إصدار يدوي للعملات في هذه المرحلة؛ لا صلاحية مالية لأي حساب حالي.

## 7. قواعد الدفتر والتسوية

- دفتر العملات append-only: لا UPDATE أو DELETE من مسارات اللعبة. التصحيح حركة عكسية/تعويضية جديدة تشير للحركة الأصلية وبسبب معتمد.
- كل سطر دفتر يمثل عملة واحدة واتجاهًا واحدًا ومبلغًا موجبًا. لا يجمع Cash وChips وGems في صف مبلغ متعدد العملات.
- الرصيد المخزن snapshot لتسريع القراءة؛ دفتر الحركات هو سجل التدقيق لإعادة الحساب والمطابقة.
- يجب أن يتطابق مجموع الحركات الموقعة لكل حساب/عملة مع snapshot وفق نقطة البداية/الرصيد الافتتاحي الموثق.
- الحركات الافتتاحية من الترحيل تكون نوعًا مستقلًا مرتبطًا ببصمة مصدر الترحيل، ولا تُعامل كمكافأة جديدة.
- تُنشأ تقارير كشف التكرار، اختلاف snapshot عن ledger، ملكية بلا مرجع، مرجع شراء بلا ملكية، وحركة غير مرتبطة بطلب.
- لا تُعدّل بيانات الدفتر التاريخية لإصلاح فروقات التسوية.

## 8. سياسة الكتالوج والاستحقاقات

- الكتالوج يملك أسعار المنتجات والخدمات والعملات وحالة الإتاحة وإصدار القواعد.
- لا يصبح أي عنصر قابلًا للشراء لمجرد وجود سعر قديم في سكربت.
- قيم المركبات ذات السعر صفر أو سالب لا تفسر على أنها موافقة لفتح منتجات؛ عناصر السعر السالب غير متاحة حاليًا، والصفر لا يعتمد عرضًا مجانيًا جديدًا.
- ألوان Horus والأسعار القديمة تسجل كبيانات جرد فقط حتى اعتمادها ضمن الاقتصاد الموحد.
- متجر الملابس القديم خارج التشغيل نهائيًا وفق قرار الشخصيات الجاهزة.
- الإيجار خدمة مؤقتة في الكتالوج إذا اعتمد تشغيله، مع معرف طلب ثابت لا يعتمد ticks أو ساعة العميل.
- المهام والوظائف والإنجازات والأنشطة اليومية والصناديق والزيارات والفعاليات تستخدم Entitlement Service. لا تنشأ مكافأة أو قيمة غير معتمدة.
- صندوق المكافأة الفرعوني يبقى عنصرًا بصريًا وتفاعليًا فقط حتى تفعيل النظام الموحد؛ لا تُفعّل إعداداته المالية الحالية.

## 9. أمن Supabase وRLS

- المخطط الخاص لا يكون مكشوفًا عبر Data API. لا يُمنح العميل صلاحيات مباشرة على wallet أو ledger أو catalog الداخلي أو requests أو ownership.
- RLS دفاع إضافي على الجداول التي قد تُعرض لأي دور، مع سياسات ملكية دقيقة؛ لا تعتبر `TO authenticated` وحدها تفويضًا لقراءة صفوف الآخرين.
- لا تعتمد الصلاحيات على `user_metadata` القابل لتعديل المستخدم.
- يجب مراجعة كل دالة مرتفعة الصلاحية: تحقق auth داخلها، schema غير مكشوف، search_path آمن، صلاحيات EXECUTE محددة، واختبارات anon/authenticated.
- لا تُنشأ أو تعدل كائنات في schema `realtime`; توضح تحديثات Supabase الحالية أن المخطط مقفل ضد التعديلات، مع بقاء دعم سياسات RLS على `realtime.messages`.
- عند إنشاء جداول جديدة في `public` لا تفترض أنها أصبحت متاحة تلقائيًا عبر Data API؛ سياسة Supabase الحديثة غيّرت التعريض الافتراضي. التصميم هنا يتجنب نشر جداول الاقتصاد أصلًا.
- بعد أي تنفيذ فعلي: اختبارات SQL/pgTAP، مراجعة RLS والصلاحيات، ثم Supabase Advisors للأمان والأداء.

## 10. اختبارات قبول قبل أي تفعيل

1. طلب شراء متكرر بنفس request_id ينشئ خصمًا واحدًا وملكية واحدة.
2. إعادة استخدام request_id مع بيانات مختلفة تُرفض.
3. طلبان متزامنان على آخر رصيد/وحدة لا ينتجان رصيدًا سالبًا أو ملكية مزدوجة.
4. طلبا مطالبة متزامنان للاستحقاق نفسه ينتجان مطالبة واحدة.
5. فشل إنشاء الملكية بعد محاولة الخصم يؤدي إلى rollback كامل.
6. انقطاع العميل بعد commit ثم الاستعلام بنفس request_id يعيد النتيجة السابقة.
7. anon وauthenticated غير المالك لا يستطيعون قراءة أو تعديل بيانات الاقتصاد.
8. تغيير account_id أو player_id في payload لا يغير هوية صاحب الطلب.
9. لا يستطيع العميل تعديل السعر أو العملة أو مقدار المكافأة.
10. قيم BIGINT الكبيرة تمر عبر RPC/JSON دون فقد دقة، والقيم خارج النطاق تُرفض.
11. اختبار عكس معاملة دون تعديل السطر الأصلي.
12. مطابقة snapshot مع ledger وإثبات الاستعادة من نسخة احتياطية.
13. اختبار XP منفصلًا عن أرصدة العملات.
14. اختبار انقطاع الشبكة وتجديد Auth وإعادة المحاولة الآمنة.
15. اختبار حسابين مصادقين منفصلين دون استخدام حساب المؤسس الحقيقي.

## 11. مراحل التنفيذ المقترحة

| المرحلة | العمل | مخرجاتها وبوابة الخروج |
|---|---|---|
| T0 | مراجعة التصميم مع جرد E0 والمخطط الحالي | قائمة جداول/دوال قابلة لإعادة الاستخدام وتعارضات موثقة |
| T1 | مخطط DB تفصيلي وقيود وفهارس وسياسات وصول | مراجعة SQL والأمان قبل أي migration |
| T2 | دفتر ومحفظة وidempotency في مشروع اختبار معزول | اختبارات الذرية والتزامن والدقة ناجحة |
| T3 | كتالوج واستحقاقات وملكية وXP منفصلة | اختبارات قواعد الخادم والملكية |
| T4 | واجهة Godot موحدة وقراءة snapshot | لا كتابة مالية محلية من الواجهات |
| T5 | محول قراءة قديم وتقارير مطابقة جافة | تعارضات مرئية ولا أثر مالي جديد |
| T6 | ترحيل تجريبي بحسابات اختبار مصرح بها | تطابق كامل وإعادة تشغيل آمنة |
| T7 | اختبارات Android وحسابين/أكثر ومراجعة مستقلة | نجاح موثق لكل بوابة |
| T8 | طلب قرار تشغيل صريح | لا تفعيل أو إنتاج قبل موافقة المستخدم |

## 12. حدود التنفيذ في هذه الدفعة

- لم تُنشأ جداول أو RPC أو migrations.
- لم تُنفذ تغييرات على Supabase الاختباري أو الإنتاجي.
- لم تُعدل ملفات scripts أو أسعار أو مكافآت أو أرصدة أو ملكيات.
- لم تُنشأ حسابات أو تُستخدم هوية المؤسس.
- لم يُنفذ ترحيل بيانات أو تفعيل مالي.
- هذه وثيقة تصميم وليست إثباتًا على وجود هذه المكونات في قاعدة البيانات.

# الاستكمال الشامل: مركز إدارة الاقتصاد والحوكمة والتشغيل

**الحالة:** تصميم مقترح فقط. يوسع هذا القسم المعمارية السابقة لتشمل إدارة الاقتصاد ومراقبته، ولا يمثل تنفيذًا أو إذنًا بالتشغيل.

## 14. مركز الاقتصاد المركزي

يتكون النظام من طبقتين لا تنفصلان:
1. **محرك المعاملات:** ينفذ قراءة الرصيد والشراء والصرف والاستحقاق والملكية والدفتر بصورة ذرية.
2. **مركز التحكم والحوكمة:** يدير السياسات والإصدارات والتفعيل والإيقاف والحدود والمصادر والمصارف والمراجعة والمراقبة.

لا يجوز لأي مبنى أو نشاط أو آلة أو متجر أو واجهة امتلاك منطق مالي مستقل. جميعها تتصل عبر بوابة اقتصاد واحدة، والخادم وحده يقرر السماح بالعملية وينفذها.

المكونات المركزية المطلوبة:
- Economy Gateway: نقطة دخول موحدة تتحقق من الجلسة والطلب.
- Wallet Service: محفظة واحدة لكل لاعب، دون محافظ فرعية.
- Ledger & Accounting: دفتر محاسبي غير قابل للمحو أو التعديل.
- Source Registry وSink Registry: سجل شامل لمصادر إصدار العملة ومصارف استهلاكها.
- Catalog & Pricing: كتالوج مركزي للمنتجات والخدمات والأسعار والإتاحة.
- Entitlement Service: التحقق من الأهلية ومنح الاستحقاقات.
- Ownership Service: تسجيل ملكية العناصر والخدمات.
- Machine/Activity Adapters: ربط الآلات والأنشطة بالمركز دون منطق مالي محلي.
- Policy Engine: تطبيق القواعد والإصدارات والحدود.
- Risk & Abuse Monitor: رصد الأنماط غير الطبيعية.
- Reconciliation Service: مطابقة الأرصدة والدفتر والملكية.
- Economy Analytics: تقارير الإصدار والاستهلاك والتضخم.
- Admin Operations: أدوات مراجعة واعتماد وإيقاف بصلاحيات منفصلة ومدققة.

## 15. سجل المصادر والمصارف والآلات

يجب أن يسجل كل مصدر أو مصرف بمعرف ثابت، ونوع النظام، والعملة، وقاعدة الأهلية أو السعر، وحدود التكرار، وإصدار السياسة، وحالة التفعيل، ومالك التكامل، ونتائج الاختبارات.

### مصادر الإصدار التي يجب حصرها
المهام والوظائف، الإنجازات، الأنشطة اليومية، الفعاليات، الصناديق، زيارات الشقق، وأي آلات أو أجهزة أو أنشطة في المدينة قد تصدر عملة، إضافة إلى أي مصدر مستقبلي.

كل مصدر يحتاج مرجع حدث موثوقًا من الخادم، وهوية مستخرجة من الجلسة، ووقتًا خادميًا، ومفتاح منع تكرار، وإصدار قاعدة. الضغط على زر أو مشاهدة عنصر لا يثبت وحده استحقاق المكافأة.

### مصارف العملة التي يجب حصرها
المركبات، ألوانها أو خصائصها المعتمدة، الأثاث، مقتنيات الشقق، الإيجارات، الخدمات، المتاجر، الآلات التي تتطلب دفعًا، وأي خدمة مدفوعة مستقبلية.

إدراج عنصر في السجل لا يعني السماح ببيعه أو اعتماد سعر له. تظل الأسعار والإتاحة غير نشطة حتى اكتمال النظام وموافقة المستخدم.

### سجل الآلات
ينشأ سجل للآلات بعد حصرها الفعلي، يتضمن معرف الآلة، موقعها، نوعها، وصف وظيفتها المعتمد، نوع تفاعلها، تصنيفها كمصدر أو مصرف أو غير مالية، adapter المرتبط بها، إصدار السياسة، حالة التفعيل ونتائج الاختبار.

لا نخترع وظيفة أو مكسبًا أو تكلفة لأي آلة. مراجعة ملفات المصدر السابقة لم تثبت حصر كل الأصول المرئية أو التصاميم؛ لذلك يظل فحص مشاهد Godot والأصول ومراجع التصميم بندًا مفتوحًا، ولا يعلن اكتمال ربط الآلات قبل إغلاقه.

## 16. المحاسبة الموحدة وإصدار العملات

يجب تطوير نموذج الدفتر إلى قيود مزدوجة (Double-entry journal) حتى يمكن تتبع إجمالي الإصدار والاستهلاك:
- كل حدث اقتصادي ينشئ قيدًا محاسبيًا واحدًا أو أكثر، مع سطور متوازنة لكل عملة.
- مجموع المدين والدائن لكل قيد ولكل عملة متوازن.
- حسابات الإصدار والخزينة والاستهلاك والتسوية حسابات محاسبية داخلية، وليست محافظ لاعبين ولا تسمح بتحويل بين اللاعبين.
- إصدار العملة يقابله حساب إصدار مركزي وسبب ومصدر موثوق وسياسة سارية.
- استهلاك العملة يقابله حساب استهلاك أو خدمة.
- الشراء والخصم والملكية تحفظ في معاملة ذرية واحدة.
- لا تداول بين اللاعبين ولا تحويل عملة إلى عملة ولا عملة رابعة.
- القيود التاريخية append-only؛ التصحيح بقيد عكسي مرتبط بالأصل مع السبب والمراجعة، وليس بتعديل السجل الأصلي.

هذا تطوير تصميمي للنموذج الأولي في القسم 3، ويجب إقرار مخطط الحسابات وقواعد التوازن قبل كتابة SQL.

## 17. حوكمة السياسات والإصدارات وفصل الصلاحيات

كل سياسة اقتصادية يجب أن تكون ذات إصدار محفوظ تاريخيًا، يشمل المصدر أو المصرف أو المنتج، العملة، شروط الأهلية والتكرار، الحدود، السعر أو المكافأة عند اعتمادها مستقبلًا، توقيت السريان الخادمي، الحالة، سبب التغيير، مقدم الطلب، المراجع، المعتمد وبصمة الإصدار.

حالات السياسة: مسودة، مراجعة، معتمدة، مجدولة، نشطة، متوقفة، متقاعدة. لا تعدل السياسة القديمة بأثر رجعي؛ تحفظ كل معاملة إصدار السياسة الذي حكمها.

فصل الصلاحيات المقترح:
- اللاعب: قراءة محفظته وطلب العمليات المسموحة فقط.
- خدمة اللعبة: إرسال مراجع أحداث موثوقة دون تعديل مباشر للرصيد.
- المراقب الاقتصادي: قراءة التقارير دون إصدار أو خصم.
- مراجع السياسة: مراجعة المقترحات دون اعتماد منفرد.
- معتمد التشغيل: صلاحية مقيدة لا تمنح إلا بعد اعتماد صريح.
- المسؤول الأمني: إيقاف مسار عند حادث وفق صلاحية منفصلة.

لا تُمنح أدوار مالية تلقائيًا لأي حساب، ولا يفترض امتلاك حساب المؤسس أو حساب الاختبار صلاحيات مالية. تعيين الأدوار الحساسة يحتاج موافقة مستقلة.

## 18. مفاتيح الإيقاف والتحكم الآمن

يجب أن تكون مفاتيح التحكم خادمية لا تعتمد على إخفاء الأزرار في Godot:
- إيقاف كل عمليات العملات مع السماح بقراءة آخر رصيد موثوق.
- إيقاف الشراء وحده.
- إيقاف المطالبات والمكافآت وحدها.
- إيقاف مصدر أو مصرف أو آلة محددة.
- وضع صيانة يمنع بدء معاملات جديدة ويسمح بالاستعلام عن نتائج الطلبات السابقة.

يسجل كل تغيير سبب الإيقاف ونطاقه ووقته وهوية منفذه. إذا تعذر التحقق من حالة التفعيل، يرفض النظام العملية المالية الجديدة (fail closed)، ولا يعود إلى منطق محلي قديم.

## 19. المراقبة والتحليلات والتضخم

تحتاج الإدارة إلى لوحة قراءة وتحليل منفصلة عن واجهة اللاعب، تعرض:
- إجمالي Cash وChips وGems المتداولة، وإجمالي الإصدار والاستهلاك لكل فترة.
- توزيع الأرصدة بصورة مجمعة لا تكشف هويات اللاعبين.
- صافي التدفق لكل مصدر ومصرف وأعلى المصادر أثرًا.
- نسبة الإصدار إلى الاستهلاك واتجاهها.
- سرعة دوران العملة وتركيز الأرصدة وتراكمها.
- معدلات المطالبات والمشتريات المكررة والفاشلة.
- فروقات التسوية والقيود غير المتوازنة والملكية غير المبررة.
- مؤشرات إساءة الاستخدام والتزامن.
- حالة كل تكامل ومصدر ومصرف وآلة واختبار.

لا يحدد التصميم الآن هدف تضخم أو سقف أرصدة أو سعرًا أو قيمة مكافأة. لكنه يفرض قياس نمو المعروض النقدي، وصافي الإصدار، وتراكم العملات، وتركيز الثروة، واعتماد الاقتصاد على مصادر محدودة، ومدى استيعاب المصارف للإصدار. أي تغيير اقتصادي مستقبلًا يحتاج تقرير أثر موثقًا واعتمادًا صريحًا، ولا تنفذه لوحة التحليلات آليًا.

## 20. كشف الإساءة والنزاعات والتصحيح

يرصد النظام تكرار الطلبات غير الطبيعي، وتغيير هوية الحساب، وتكرار مرجع الاستحقاق، وتجاوز الحدود، والتزامن غير المعتاد، ومحاولات شراء عنصر غير متاح، واختلاف حالة العميل عن الخادم.

الإشارة ليست وحدها دليلًا كافيًا لمعاقبة اللاعب. تحفظ أدلة الطلب والسياسة والمرجع والنتيجة. أي تعويض أو عكس معاملة يحتاج صلاحية منفصلة وسببًا ومرجع الحركة الأصلية ومراجعة مناسبة. لا يعدل الرصيد يدويًا بلا قيد مقابل، ولا تكشف قواعد مكافحة الإساءة الحساسة للعميل.

### شروط إغلاق الجرد
لا يعلن اكتمال التكامل قبل مراجعة جميع ملفات GDScript ومشاهد TSCN وموارد TRES، وعناصر التفاعل المرئية ومراجع الآلات، ومواضع كتابة ConfigFile وتعديل العملات وواجهات الشراء والمكافآت، وكل RPC وجداول Supabase القديمة، وكل أنظمة الملكية والحفظ المحلي. تصنف النتائج إلى: مركزي، غير مالي، قديم/متوقف، غير محسوم، أو يحتاج ترحيلًا آمنًا. لا تحذف بيانات قديمة قبل النسخ الاحتياطي والمطابقة والاعتماد.

## 22. التسوية والاستعادة

تجرى مطابقة دورية بين المحفظة والدفتر والحسابات المقابلة، ومطابقة منفصلة بين الشراء والملكية والإيصالات. تنشأ تقارير عن المصدر بلا استحقاق، والاستحقاق بلا حركة مطلوبة، والحركة بلا حدث موثق. تختبر النسخ الاحتياطية والاستعادة في بيئة اختبار مع توثيق أهداف الاستعادة قبل الإطلاق. يمكن إعادة بناء snapshot من الدفتر دون تعديل القيود الأصلية. عند اكتشاف خلل يوقف المسار المتأثر وتحفظ الأدلة وتتم المطابقة قبل أي تعويض.

## 23. بوابات قبول النظام الموحد

لا يعد النظام مكتملًا بمجرد توحيد شاشة الرصيد أو نجاح شراء واحد. يجب إغلاق جميع البوابات:
1. حصر كل مصدر ومصرف ونظام وآلة معروفة وتصنيفها.
2. إزالة كل كتابة مالية محلية مستقلة قابلة للاستخدام.
3. دفتر متوازن محاسبيًا وقابل للتتبع وغير قابل للمحو.
4. ذرية الرصيد والدفتر والطلب والاستحقاق والملكية.
5. نجاح اختبارات RLS وRPC والصلاحيات والحسابات المتعددة.
6. عمل إصدارات السياسات وفصل الصلاحيات وسجل الاعتماد.
7. اختبار مفاتيح الإيقاف والفشل الآمن.
8. عمل تقارير الإصدار والاستهلاك والتضخم والتسوية.
9. نجاح اختبارات التزامن وإعادة المحاولة ومكافحة التكرار والنزاعات.
10. مطابقة الأرصدة والملكيات القديمة أو توثيق الاستثناءات دون حذف مبكر.
11. اختبارات خادمية وGodot وAndroid وحسابين أو أكثر بنتائج فعلية.
12. مراجعة نهائية وموافقة المستخدم الصريحة على التشغيل.

## 24. تعريف الاكتمال وحدود هذه الإضافة

اكتمال النظام يعني اكتمال جميع الطبقات السابقة واختبارها معًا، لا مجرد وجود محفظة واحدة. وحتى بعد اكتمال البناء والاختبار يظل الاقتصاد مغلقًا ماليًا إلى أن تصدر موافقة تشغيل صريحة. اكتمال النظام لا يعتمد تلقائيًا أي سعر أو مكافأة أو حد أو تشغيل معاملة حقيقية.

**حدود هذا التحديث:** توثيق وتصميم فقط؛ لا migrations أو SQL أو تغييرات Supabase، ولا تعديل سكربتات أو أرصدة أو أسعار أو مكافآت أو ملكيات، ولا تفعيل لأي مصدر أو مصرف.
