# تجهيز التحقق من بريد المؤسس

هذه طبقة عميل جاهزة للربط، وليست خدمة مصادقة منشورة. لا تعتبر كتابة البريد أو إدخال رمز PIN إثباتًا لملكية حساب المؤسس.

## إعداد عنوان الخدمة
بعد نشر خدمة HTTPS موثوقة، اضبط في إعدادات المشروع:
`founder/auth/api_base_url` = عنوان الأساس دون شرطة مائلة أخيرة، مثل `https://auth.example.com`.
لا تضع مفاتيح خاصة أو أسرار خادم داخل تطبيق Godot.

## واجهات الخادم المطلوبة

### POST /v1/founder/email/request-code
الطلب:
```json
{"email":"user@example.com"}
```
أرسل رمزًا مؤقتًا إلى البريد بعد تطبيق rate limiting. يجب أن تكون رسالة النجاح عامة حتى لا تكشف هل البريد مسجل أو مؤهل.

### POST /v1/founder/email/verify-code
الطلب:
```json
{"email":"user@example.com","code":"123456"}
```
لا تصدر استحقاق المؤسس إلا بعد التحقق من الرمز ومطابقة البريد المؤهل بهوية المؤسس الوحيدة على الخادم. لا تسمح للعميل باختيار founder_id أو subject_id أو الرتبة.

الاستجابة الناجحة:
```json
{
  "entitlement_payload":"النص الأصلي الموقّع كما هو",
  "signature":"توقيع RSA/SHA-256 بصيغة Base64"
}
```

يجب أن يحتوي النص الأصلي الموقّع على الأقل على:
- `founder_id`: القيمة الثابتة `king_of_egypt_city:founder:primary`
- `subject_id`: معرف ثابت صادر من الخادم.
- `offline_allowed`: قيمة Boolean.
- `issued_at` و`expires_at`: Unix timestamps.

يوقع الخادم النص الأصلي باستخدام المفتاح الخاص خارج اللعبة. يضبط التطبيق المفتاح العام المقابل في `founder/security/public_key_pem`. لا تضع المفتاح الخاص في المستودع أو التطبيق.

## ضوابط أمنية قبل الإطلاق
- HTTPS فقط، وتقييد المحاولات وإعادة إرسال البريد وانتهاء صلاحية الرمز على الخادم.
- ربط البريد المؤكد بحساب المؤسس على الخادم، لا بمجرد تطابق نص البريد.
- لا ترسل PIN إلى الخادم ولا تحفظه هناك؛ PIN قفل محلي منفصل.
- استعادة PIN أو نقل الحساب إلى جهاز جديد يتطلب تحققًا جديدًا من البريد وإصدار تذكرة جديدة.
- صلاحيات الإدارة والاقتصاد المشترك يجب أن تتحقق خادميًا في كل عملية حساسة.
- لم يتم إنشاء الخادم أو إرسال بريد فعلي أو ضبط مفتاح عام؛ يلزم نشر الخدمة وإعداد المفتاح قبل تفعيل الدخول.
