# ربط توليد Tripo من داخل اللعبة

## الهدف
إزالة الحاجة إلى نافذة Supabase Test اليدوية. تستعمل أداة المؤسس جلسة Supabase النشطة من `PlayerAccountAuthClient`، ولا تتعامل مع مفتاح Tripo مطلقًا.

## الملفات
- `scripts/tripo_model_generator_client.gd`: واجهة مؤسس صغيرة تظهر فقط عند وجود تذكرة مؤسس موثقة وجلسة صالحة تطابق حساب المؤسس.
- `project.godot`: تسجيل العميل كـ Autoload.

## تدفق العمل
1. يسجل المؤسس الدخول عبر Google بالطريقة الحالية.
2. يكتمل التحقق من التذكرة الموقعة، وتطابق `founder_subject_id` مع جلسة المستخدم.
3. تظهر أداة Tripo داخل اللعبة.
4. يضغط المؤسس زر «إنشاء الخيمة الملكية الرئيسية» لبدء مهمة واحدة؛ لا يبدأ التوليد تلقائيًا عند تشغيل اللعبة.
5. يرسل العميل `POST` إلى Edge Function مع `Authorization: Bearer <user access token>` و`apikey` publishable key.
6. تحفظ الأداة `task_id` محليًا، ويمكن متابعة الحالة دون إنشاء مهمة أخرى.
7. عند اكتمال Tripo، ينزّل العميل ملف GLB وصورة المعاينة من الروابط التي أعادتها المهمة ويحفظهما في مجلد بيانات اللعبة.

## الأمان
- مفتاح `TRIPO_API_KEY` يبقى في Supabase Edge Function Secrets فقط.
- لا يجري تخزين Access Token في ملف جديد أو طباعته في السجلات؛ يستعمل من ذاكرة عميل المصادقة الحالية.
- لا تتجاوز الواجهة فحوص المؤسس، كما تظل Edge Function مسؤولة عن التحقق من الجلسة وقائمة السماح.
- لا يوجد تعديل لـ `verify_jwt` أو أسرار Supabase أو كود الإنتاج في هذا الفرع.

## ملاحظات وحدود التحقق
- هذه إضافة عميل إلى الفرع فقط؛ لم تُدمج في `main` ولم تُنشر.
- لا يمكن تأكيد نجاح اتصال Tripo أو صلاحية الأسرار/قائمة السماح من هذا التغيير وحده.
- لم يبدأ توليد أي أصل ولم يُستهلك رصيد Tripo بواسطة هذا التغيير.
- يلزم فحص CI/Godot على الفرع ومراجعة استجابة Edge Function الفعلية قبل الدمج.
- لا يُدمج ملف GLB في المدينة تلقائيًا. يجب فتح الملف في Godot وعرض معاينة مباشرة من نفس GLB النهائي، ثم أخذ موافقة المؤسس قبل الدمج.
