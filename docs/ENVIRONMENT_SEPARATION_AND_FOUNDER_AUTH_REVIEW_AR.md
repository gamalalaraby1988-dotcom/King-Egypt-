# مراجعة فصل TEST عن PRODUCTION ومصادقة المؤسس

**تاريخ المراجعة:** 2026-11-25  
**الفرع:** `integration/safe-mainline-audit`  
**النطاق:** قراءة فقط؛ لا تغييرات على قواعد البيانات أو إعدادات المشاريع أو الفروع التشغيلية.

## 1) ملخص تنفيذي

- مشروع الاختبار `KING_OF_EGYPT_CITY_TEST` نشط، ومشروع الإنتاج `KING_OF_EGYPT_CITY_PRODUCTION` نشط.
- ملف `project.godot` في `main` يوجّه إعدادات Auth إلى مشروع PRODUCTION.
- طلب الدمج #156 يغيّر الإعدادين نفسيهما إلى مشروع TEST، رغم أن وجهته `main`. دمجه كما هو سيحوّل إعداد الاتصال الافتراضي في نسخة main إلى TEST؛ لذلك لا يُعتمد قبل معالجة فصل البيئات.
- عميل المؤسس يستدعي Edge Function باسم `founder-entitlement`، لكن جرد Edge Functions وفحص الاسم مباشرة لم يجدا هذه الوظيفة في TEST أو PRODUCTION.
- لا يُثبت الفحص الحالي أن استحقاق المؤسس مربوط خادميًا بحساب Auth الحالي؛ يلزم تنفيذ/نشر endpoint موثوق والتحقق من تطابق `subject_id` مع `auth.uid()` ومعرّف المؤسس المسموح به قبل الاعتماد.

## 2) مقارنة بيئتي Supabase

| البند | TEST | PRODUCTION |
|---|---:|---:|
| الحالة | ACTIVE_HEALTHY | ACTIVE_HEALTHY |
| إصدار PostgreSQL | 17.11.0.019 | 17.12.0.000 |
| migrations المسجلة | 63 | 7 |
| الجداول في مخططات التطبيق المحسوبة (public/private/game_test/game_private) | 48 | 6 |
| Edge Functions النشطة | 7 | 1 |

الجداول أعلاه محسوبة من مخططات التطبيق المذكورة، ولا تشمل مخططات Supabase الداخلية. لدى TEST مخططات اختبار إضافية مثل `game_test` و`game_private` لا تظهر ضمن قاعدة الإنتاج الحالية.

**الاستنتاج:** البيئتان ليستا متزامنتين ولا يجوز اعتبار TEST نسخة مطابقة من PRODUCTION. لا تُنقل migrations أو Edge Functions أو إعدادات Auth تلقائيًا من TEST إلى PRODUCTION.

## 3) طلب الدمج #156 — تسجيل الدخول بالبريد وكلمة المرور

- PR #156 مفتوح وغير مدمج، والوجهة `main`.
- الفرع: `staging/email-auth-session`.
- التغيير في `project.godot` يستبدل عنوان ومفتاح النشر الخاصين بـ PRODUCTION بقيم TEST.
- إعداد `main` الحالي ما زال يشير إلى PRODUCTION؛ لذا فإن هذا الفرق في PR مانع دمج واضح.
- التغيير يضيف تسجيل الدخول لحساب لديه مسبقًا اعتماد بريد/كلمة مرور؛ ولا ينشئ حسابًا جديدًا ولا يربط كلمة مرور بحساب Google-only تلقائيًا، وفق وصف PR.
- الكود يمرر الاستجابة إلى مسار قبول الجلسة المشترك، ويتحقق من وجود بريد مؤكد، ويستخدم مخزن Android الآمن لحفظ refresh token عند توفره.
- استعادة الجلسة على Android ما زالت مشروطة بتضمين مكوّن التخزين الآمن في APK واختباره على جهاز فعلي؛ نجاح فحوص المصدر/CI وحده لا يثبت ذلك.
- توجد رسالة نجاح داخل مسار قبول الجلسة تشير إلى Google حتى عند تسجيل الدخول بالبريد؛ هذه ملاحظة UX صغيرة يجب تصحيحها.
- لم يتم فحص حسابات المستخدمين أو تغيير كلمات المرور أو إنشاء حسابات.

## 4) استحقاق المؤسس وربط الهوية

- `FounderAuthClient` يستدعي `/functions/v1/founder-entitlement` باستخدام access token للحساب الحالي.
- جرد Edge Functions في TEST يعرض: `game-proof-issuer`, `game-puzzle-piece-issuer`, `player-sync`, `slot-machine-settlement`, `slot-machine-spin`, `jet-ski-race-results`, `city-session-directory`.
- جرد PRODUCTION يعرض `tripo-model-generator` فقط.
- طلب الحصول على الوظيفة `founder-entitlement` مباشرة أعاد Function not found في كلا المشروعين.
- `FounderIdentityManager` يتحقق من توقيع تذكرة الاستحقاق ومُعرّف المؤسس الثابت، ويتطلب وجود `subject_id` وانتهاء صلاحية مستقبلية. ربط `subject_id` بالحساب المصادق عليه يجب أن يُفرض في الخادم الذي يصدر التذكرة، لا أن يُترك لقيمة يرسلها العميل.
- قبل تشغيل مسار المؤسس: يجب أن يتحقق الخادم من JWT، ويستخرج هوية المستخدم من سياق Auth الموثوق، ويتحقق من تطابقها مع هوية المؤسس المسموح بها، ويوقّع تذكرة قصيرة/محددة الصلاحية. يجب ألا يحتوي العميل على مفتاح توقيع خاص أو service-role key.
- لا توجد أدلة من هذا الفحص على وجود وظيفة إصدار استحقاق منشورة؛ لذلك لا يمكن اعتبار التحقق النهائي من هوية المؤسس جاهزًا.

## 5) ملاحظات أمان قاعدة البيانات

- تحذير Auth `auth_leaked_password_protection` موجود في TEST وPRODUCTION: حماية كلمات المرور المسرّبة غير مفعّلة. يوصى بتقييم وتفعيل الإعداد في كل مشروع على حدة قبل إتاحة التسجيل/تغيير كلمات المرور على نطاق واسع.
- Advisor يعرض ثماني دوال صديقة في مخطط `public` من نوع SECURITY DEFINER قابلة للتنفيذ من authenticated في كلا المشروعين. فحص التعريفات أظهر أنها wrappers تستدعي دوال `private` المقابلة، لكن هذا لا يغني عن مراجعة صلاحيات EXECUTE وفحوص `auth.uid()` في كل دالة داخلية. لا يُصنّف التنبيه وحده كدليل اختراق.
- Advisor يعرض جداول RLS مفعّلًا عليها دون سياسات: 27 في TEST و3 في PRODUCTION. قد يكون غياب السياسات مقصودًا كمنع وصول مباشر، خصوصًا للمخططات الخاصة؛ يجب توثيق نموذج الوصول عبر RPC/الخادم بدل إضافة سياسات عامة عشوائية.
- لا توجد تغييرات SQL أو إعدادات Auth أجريت خلال هذه المراجعة.

## 6) خطة التنفيذ الآمن المقترحة

1. إنشاء فصل بيئات صريح: إعدادات TEST وPRODUCTION منفصلة، ومنع تضمين قيم TEST في إعدادات إصدار الإنتاج.
2. إضافة فحص CI يرفض أي عنوان أو مفتاح مشروع TEST ضمن إعداد/حزمة إصدار PRODUCTION، والعكس حسب سياسة البناء.
3. إصلاح PR #156 على فرع مستقل: لا يدمج تغييرات Auth الخاصة بـ TEST إلى main؛ تُحفظ إعدادات main للإنتاج، وتُدار إعدادات الاختبار من إعدادات بناء منفصلة.
4. استكمال endpoint `founder-entitlement` ونشره في TEST أولًا، مع اختبار ربط `auth.uid()` بهوية المؤسس الثابتة وتوقيع التذكرة، ثم خطة نشر مستقلة للإنتاج بعد الموافقة.
5. اختبار سيناريوهات: حساب مؤسس صحيح، حساب آخر، حساب Google-only، بريد غير مؤكد، كلمة مرور خاطئة، refresh token منتهي/مستخدم سابقًا، تبديل الحساب، تسجيل الخروج، وإعادة تشغيل التطبيق.
6. بناء APK تجريبي والتحقق من تخزين refresh token واستعادته على جهاز Android فعلي قبل اعتبار الاستمرارية جاهزة.
7. مراجعة دوال SECURITY DEFINER وسياسات RLS مع اختبار صلاحيات مستخدمين مختلفين، دون إزالة أو إضافة صلاحيات على الإنتاج قبل مراجعة منفصلة وموافقة صريحة.

## 7) حدود هذا الفحص

- المراجعة قراءة فقط لجرد المشاريع، الجداول، migrations، Edge Functions، Advisors، وبعض تعريفات SQL وملفات GitHub.
- لم تُقرأ بيانات اعتماد المستخدمين أو كلمات المرور أو محتوى ملفاتهم الشخصية.
- لم يُنفذ اختبار اختراق شامل، ولم تُجرَ تجربة دخول حقيقية بحساب المؤسس، ولم يُختبر APK على هاتف فعلي.
- لم تُعدّل قاعدة TEST أو PRODUCTION، ولم يُدمج PR #156 أو أي طلب آخر، ولم يتغير `main`.
