# تدقيق مصدر منظومة الفعاليات والإعلانات — بعد اعتماد المراحل 77–79

## نطاق الفحص
تمت مراجعة ملفات المصدر الموجودة على فرع `sync-latest-approved-decisions-77-79`:
- `scripts/main.gd`
- `scripts/mission_manager.gd`
- `scripts/daily_activities.gd`
- `scripts/achievement_manager.gd`
- قائمة ملفات مجلد `scripts/` ومشاهد `scenes/`

هذا تدقيق نصي ساكن فقط؛ لم يتم تشغيل Godot أو اختبار اللعبة.

## ما يمكن إعادة استخدامه حاليًا
1. `mission_manager.gd` يدير المهام والوظائف المحلية والرصيد والخبرة والرقائق وسجل إيصالات المكافآت.
2. `complete_activity_once()` يسجل إكمال المهمة/الوظيفة ومكافأتها وتقدم النشاط اليومي وإيصالها في ملف اللاعب المحلي نفسه.
3. `daily_activities.gd` يعرض أنشطة يومية محلية، ويحسب المشي ويقرأ تقدم الوظائف والمهام من مدير المهام.
4. `achievement_manager.gd` يربط إنجازات محلية بإكمال الوظائف والمهام والمكافآت اليومية.
5. `main.gd` ينشئ مدير المهام والأنشطة والإنجازات مرة واحدة، كما ينشئ مباني المتجر والمطعم ومركز التوظيف ولوحات الوظائف الحالية. يمكن دراسة إعادة استخدام هذه البنية بدل إنشاء مدير مهام أو مكافآت مكرر.

## الفجوات المؤكدة في المصدر المفحوص
- الأنشطة اليومية الحالية ثلاثة فقط: المشي، إنجاز وظيفة، وإكمال مهمة؛ ولا يظهر في الملف نظام أسبوعي.
- لا يظهر في ملفات السكربتات الحالية مدير فعاليات مستقل، أو تنفيذ دورة البازل الملكي المعتمدة كل ثلاثة أيام، أو منطق إدارة جولات الفعاليات ونتائجها.
- لا يظهر في المصدر المفحوص ربط للماكينات أو الساحة أو VIP أو السفينة بمنظومة فعاليات موحدة.
- لا يظهر سكربت لوحة CITY NOTICE BOARD أو إدارة إعلانات وتثبيت وجمهور ومدة من جهة السيرفر.
- قائمة السكربتات الحالية تتضمن 21 ملف GDScript ولا تتضمن ملفات مخصصة للفعاليات أو لوحة الإعلانات أو خدمة خادمية لهذه الأنظمة.
- حفظ المهام والمكافآت والأنشطة الحالية محلي عبر ConfigFile؛ لا يثبت وجود خادم أو مزامنة أو صلاحيات مؤسس خادمية.

## قرار التنفيذ الآمن
- الإبقاء على `mission_manager.gd` كمصدر الأنشطة والمكافآت المحلية الحالية وعدم إنشاء نظام مكافآت موازٍ.
- قبل إضافة أي واجهة فعاليات، يجب تصميم واجهة بيانات موحدة تربط الفعاليات القائمة بمدير المهام/المكافآت الحالي، مع معرفات أحداث ثابتة وسجل استحقاق يمنع التكرار.
- يجب أن يلتزم تنفيذ البازل الملكي بجدول الدورات الثابتة كل ثلاثة أيام في `docs/WEEKLY_ACTIVITY_SCHEDULE_AR.md`، وألا يُنشأ بازل شهري أو نظام موازٍ.
- تحكم المؤسس ولوحة الإعلانات يتطلبان خدمة خادمية موثوقة للتحقق من الهوية والصلاحيات والتوقيت والجمهور والجوائز. لا تُنفذ صلاحيات حقيقية عبر زر محلي أو إعداد قابل للتعديل من العميل.
- إعادة استخدام المجسمات والمناطق الموجودة أولًا؛ لا تنشأ خريطة أو مبنى أو ماكينة جديدة لتغطية فجوة منطقية/شبكية.
- لا تُضاف مكافآت أو أسعار أو قواعد اقتصاد جديدة من دون قرار معتمد.

## ما لم يتم التحقق منه
- لم يتم فحص كل مشهد/مورد بصري أو كل ملف مضمن في الأرشيف في هذا التدقيق.
- لم يتم تشغيل المشروع أو تحليل GDScript بمحرك Godot.
- لم يتم اختبار حفظ البيانات أو فشل الكتابة أو تعدد الحسابات.
- لم يتم بناء APK أو اختبار Android.
- لم يتم الاتصال بخادم؛ لا توجد نتيجة اختبار شبكي.

## الخلاصة
المصدر يحتوي أساسًا محليًا قابلًا لإعادة الاستخدام للمهام والوظائف والمكافآت اليومية والإنجازات. أما المراحل 77–79 فتبقى قرارات معتمدة غير منفذة في المصدر المفحوص؛ وأكبر فجوة ليست واجهة رسومية، بل طبقة بيانات وخدمة خادمية موثوقة ثم ربط الأنظمة الحالية بها.


## توضيح بعد إعادة فحص إيصالات المكافآت
- يستخدم `mission_manager.gd` الدالة `grant_reward_once()` لحفظ إيصال المكافأة مع الرصيد والخبرة والرقائق في ملف اللاعب نفسه، ولا يحدّث القيم في الذاكرة إلا بعد نجاح الحفظ.
- تستعيد `daily_activities.gd` حالة المطالبة من إيصال اللاعب عبر `reconcile_reward_receipt()` عند بدء التشغيل. لذلك لا يصح وصف فشل حفظ ملف الأنشطة اليومي وحده بأنه يؤدي حتمًا إلى صرف المكافأة مرتين.
- يظل هذا منع تكرار محليًا فقط، ويعتمد اليوم على ساعة الجهاز؛ ولا يعوض التحقق الخادمي أو يمنع التلاعب بملفات الحفظ. راجع `DAILY_REWARD_SAVE_AUDIT_AR.md` للتفصيل.
