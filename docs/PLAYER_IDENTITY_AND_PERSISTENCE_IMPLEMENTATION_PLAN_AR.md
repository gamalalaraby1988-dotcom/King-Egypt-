# خطة تنفيذ هوية اللاعب وحفظ الشخصية والتقدم — KING OF EGYPT CITY

الفرع المستهدف: `feature/building-quick-travel`  
نوع العمل: خطة تنفيذ مرحلية قبل أي تعديل برمجي أو قاعدة بيانات.  
مرجع المراجعة: `PLAYER_IDENTITY_AUTH_AND_CHARACTER_PERSISTENCE_AUDIT_AR.md`

## 1) الهدف

ضمان أن كل حساب مصادقة موثق يملك هوية لاعب واحدة ثابتة، وأن الشخصية الجاهزة المختارة والتقدم الخاص به تُحمّل وتُحفظ على الخادم وتظهر نفسها على الأجهزة المختلفة، دون اختلاط بيانات الحسابات أو المساس بحساب المؤسس.

## 2) ثوابت لا يجوز تجاوزها

- العمل على فرع `feature/building-quick-travel` فقط؛ لا تعديل على `main` ولا دمج دون إذن صريح.
- حساب المؤسس الأصلي هو هوية المؤسس الوحيدة. لا إنشاء حساب مؤسس بديل، ولا نقل أو إعادة تعيين الشخصية أو الرتبة أو الممتلكات أو التقدم.
- حسابات الاختبار منفصلة، ولا تُمنح صلاحيات المؤسس أو المشرف.
- لا تطلب أو تخزن كلمات مرور أو OTP أو مفاتيح سرية في المستودع أو المحادثة أو السجلات.
- الشخصيات 16 شخصية جاهزة (8 رجال و8 نساء). لا خزانة أزياء ولا تخصيص ملابس/شعر ولا إعادة تفعيل متجر الملابس القديم.
- لا تجعل ConfigFile المحلي مصدرًا موثوقًا لهوية اللاعب أو التقدم أو الملكيات أو الأرصدة.
- إعدادات الجهاز مثل الصوت والجودة واللغة والتحكم تظل محلية ومنفصلة عن ملف اللاعب.
- لا تغييرات مالية أو تفعيل مكافآت أو أسعار. الاقتصاد الموحد مؤجل حتى اكتماله واختباره واعتماده الصريح.

## 3) التصميم المستهدف

### 3.1 الهوية

تسلسل الربط:

`Auth UID موثّق → سجل لاعب واحد → رمز لاعب عام ثابت`

- يفرض الخادم قيدًا فريدًا على هوية المصادقة لضمان لاعب واحد لكل حساب.
- لا يختار العميل UID ولا يرسل هوية لاعب بديلة لإثبات الملكية.
- جميع عمليات قراءة وكتابة ملف اللاعب تستخرج هوية الحساب من جلسة موثقة على الخادم.
- رمز اللاعب العام للبحث الاجتماعي ليس سرًا ولا بديلًا عن Auth UID.
- إعادة التثبيت أو تغيير الهاتف لا تنشئ لاعبًا جديدًا؛ تستعيد السجل نفسه بعد المصادقة.

### 3.2 ملف اللاعب

يُصمم ملف لاعب خادمي واحد، مع فصل المجالات داخله منطقيًا:
- الهوية العامة: معرف اللاعب ورمز اللاعب وتاريخ الإنشاء.
- الشخصية: `selected_character_id` من قائمة معرفات ثابتة للشخصيات الـ16.
- التقدم: المستوى وXP والإنجازات والمهام والأنشطة التي تقرر أن تكون دائمة.
- الملكيات: مراجع الملكيات غير المالية فقط، مع بقاء أي ملكيات ذات قيمة اقتصادية تحت بوابة الاقتصاد الموحد.
- بيانات اجتماعية مسموح بها: الاسم العام وفق سياسة تغيير الاسم اليومية المعتمدة، دون نسخ بيانات خاصة غير لازمة.

لا تُضمّن refresh token أو access token أو بيانات اعتماد داخل ملف اللاعب.

### 3.3 إعدادات الجهاز

ملف مستقل محليًا لكل تثبيت/جهاز يضم فقط:
- الصوت.
- الجودة الرسومية.
- اللغة.
- إعدادات التحكم والحساسية.
- تفضيلات واجهة غير مرتبطة بحساب بعينه.

لا يحتوي هذا الملف على رصيد أو ملكيات أو تقدم أو هوية مصادقة أو اختيار شخصية نهائي.

### 3.4 الجلسة

- استخدام آلية تخزين آمن معتمدة على Android Keystore عبر تكامل موثوق، لا ملف ConfigFile أو نص عادي.
- لا تنفيذ لتخزين الرموز قبل مراجعة دورة حياة الجلسة، وإلغاء الجلسة، وتدوير refresh token، ومعالجة فقدان المفتاح.
- إذا لم تتوفر جلسة صالحة، يطلب التطبيق تسجيل الدخول مجددًا بدل إنشاء هوية جديدة أو استخدام ملف لاعب غير معروف.
- لا تُسجل الرموز أو OTP أو رؤوس Authorization في السجلات.

## 4) مراحل التنفيذ المقترحة

### المرحلة A — جرد وتثبيت عقد البيانات

1. جرد كل حقول `kings_city_profile.cfg` ومصادر كتابتها وقراءتها.
2. تصنيف كل حقل: إعداد جهاز، تقدم لاعب، بيانات اجتماعية، بيانات اقتصادية/ملكية، أو بيانات مؤقتة.
3. تحديد ما الذي سيُنقل للخادم وما الذي يبقى محليًا.
4. تعريف قائمة معرفات الشخصيات الـ16 ومطابقتها مع الأصول النهائية قبل كتابة منطق الاختيار.
5. توثيق إصدار مخطط ملف اللاعب وقواعد التوافق والترحيل.

**بوابة A:** لا يبدأ تنفيذ التخزين أو النقل حتى يعتمد المستخدم خريطة الحقول وقائمة الشخصيات ومعرفاتها.

### المرحلة B — تثبيت هوية اللاعب الخادمية

1. مراجعة مخطط اللاعب الحالي وRPC الخاص بتهيئة حساب الاختبار دون تغيير سلوكه قبل فهمه.
2. ضمان سجل واحد لكل Auth UID بقيد فريد ومعاملة خادمية آمنة.
3. جعل إنشاء/استرجاع سجل اللاعب عملية idempotent: تكرار الطلب لا ينشئ لاعبًا ثانيًا.
4. ربط رمز اللاعب العام بالسجل نفسه، ومنع تغييره عشوائيًا عند إعادة الدخول.
5. إرجاع حالة واضحة: لاعب موجود، لاعب جديد مسموح، أو رفض صلاحية.
6. الحفاظ على allowlist الاختبار كما هي وعدم توسيعها دون إذن.

**بوابة B:** اختبار خادمي لحسابين اختباريين مستقلين، وإعادة تنفيذ التهيئة للحساب نفسه دون تكرار سجل أو تبديل رمز اللاعب.

### المرحلة C — تحميل ملف اللاعب قبل دخول المدينة

1. بعد نجاح المصادقة واسترجاع هوية اللاعب، يطلب العميل ملف اللاعب من RPC موثق.
2. لا تظهر المدينة كجلسة مكتملة قبل وصول ملف اللاعب والتحقق منه.
3. تعرض الواجهة حالات التحميل/إعادة المحاولة/فشل الاتصال بوضوح.
4. عند الفشل لا تنشئ الواجهة ملفًا افتراضيًا ثم تحفظه فوق بيانات الحساب.
5. لا يسمح العميل بإرسال Auth UID أو player ID لشخص آخر في معاملات القراءة/الكتابة.

**بوابة C:** إثبات أن حسابين لا يستطيع أحدهما قراءة ملف الآخر، وأن فشل التحميل لا يكتب فوق ملف قائم.

### المرحلة D — الشخصية الجاهزة

1. اعتماد معرف فريد وثابت لكل شخصية من الشخصيات الـ16.
2. تخزين `selected_character_id` في ملف اللاعب الخادمي.
3. توفير قائمة اختيار من الشخصيات الجاهزة فقط؛ دون واجهة ملابس أو شعر.
4. التحقق خادميًا من أن المعرف المختار ضمن القائمة المعتمدة.
5. تحميل الأصل المرئي المطابق للمعرف بعد استلام ملف اللاعب.
6. حفظ الاختيار خادميًا، وإعادة تحميله عند الدخول وعلى جهاز آخر.
7. إذا كان المعرف مفقودًا/قديمًا، استخدم حالة استرداد آمنة وواضحة ولا تستبدل اختيار لاعب قائم بصمت.

**بوابة D:** تغيير الشخصية ثم الخروج والدخول، ثم الدخول من جهاز ثانٍ، مع ظهور الشخصية نفسها.

### المرحلة E — نقل التقدم ومصالحة الملفات القديمة

1. إعداد نسخة احتياطية غير قابلة للتعديل من ملف التقدم المحلي قبل أي ترحيل.
2. تحديد سياسة لكل حقل قديم: نقل، تجاهل، إعداد جهاز، أو مراجعة يدوية.
3. عدم نقل الأرصدة أو إيصالات المكافآت المحلية كحقائق مالية؛ تخضع كلها لاحقًا للاقتصاد الموحد.
4. نقل XP والإنجازات والمهام فقط وفق قواعد مصدر موثوق ومعالجة التكرار والتعارض.
5. استخدام رقم إصدار/نسخة لكل تحديث لمنع جهاز قديم من الكتابة فوق نسخة أحدث.
6. تنفيذ الترحيل idempotent مع سجل نتائج ومراجعة الحالات المتعارضة.
7. عدم حذف الملف المحلي القديم حتى اكتمال النسخ الاحتياطي والمصالحة والتحقق والموافقة.

**بوابة E:** مقارنة قبل/بعد لحسابات الاختبار، وإثبات عدم فقد التقدم أو تكراره، مع قائمة واضحة بأي حالات تحتاج قرارًا يدويًا.

### المرحلة F — استعادة الجلسة الآمنة على Android

1. تقييم خيار تكامل Android Keystore المناسب لإصدار Godot ومشروع Android.
2. حفظ refresh token فقط في مساحة آمنة محمية؛ لا تخزينه في ConfigFile أو logs.
3. اختبار تدوير الرموز، انتهاء الجلسة، إلغاء الجلسة، فقدان بيانات التطبيق، وإعادة التثبيت.
4. ضمان أن جلسة قديمة لا تُستخدم بعد تبديل الحساب.
5. عند تعذر فك التخزين الآمن، اطلب تسجيل دخول جديدًا دون إنشاء لاعب جديد.

**بوابة F:** اختبار Android فعلي على جهازين/تثبيتين، مع التحقق من عدم ظهور الرموز في الملفات والسجلات.

## 5) ترتيب الدمج والاعتماد

- كل مرحلة تُنفذ في commits صغيرة على فرع العمل فقط.
- بعد كل مرحلة: مراجعة diff، فحص static، تشغيل اختبارات Godot المتاحة، ثم CI.
- لا يُعلن نجاح بناء أو اختبار Android إلا بوجود نتيجة فعلية موثقة.
- لا تنتقل المرحلة التالية إذا فشلت بوابة قبول المرحلة الحالية.
- لا دمج إلى `main` دون موافقة صريحة.

## 6) خطة الاختبارات الشاملة

| الاختبار | النتيجة المطلوبة |
|---|---|
| نفس Auth UID يكرر تهيئة اللاعب | سجل لاعب واحد ورمز ثابت |
| حسابان على جهاز واحد | ملفان منفصلان تمامًا |
| الحساب نفسه على جهازين | نفس الشخصية والتقدم بعد المزامنة |
| محاولة قراءة UID آخر | رفض خادمي |
| فشل تحميل الملف | لا كتابة افتراضية فوق بيانات قائمة |
| اختيار شخصية جديدة | تحقق خادمي وحفظ دائم |
| معرف شخصية غير معتمد | رفض آمن |
| انقطاع الشبكة أثناء الحفظ | لا فقد ولا تكرار؛ استئناف idempotent |
| جهاز قديم يرسل نسخة قديمة | منع الكتابة فوق النسخة الأحدث |
| إعادة تثبيت التطبيق | استعادة الهوية بعد المصادقة |
| انتهاء/تدوير الجلسة | جلسة صحيحة دون اختلاط الحسابات |
| حساب المؤسس | نفس الهوية والشخصية والرتبة والممتلكات والتقدم دون تغيير |

## 7) فصل صلاحيات التنفيذ

هذه الخطة لا تمنح إذنًا تلقائيًا بـ:
- تعديل مخطط Supabase أو RLS أو RPC.
- تغيير allowlist أو صلاحيات أي مستخدم.
- تعديل حساب المؤسس أو بياناته.
- ترحيل ملفات تقدم فعلية أو حذفها.
- تفعيل نظام مالي أو مكافآت أو أسعار.
- تغيير الأصول النهائية أو افتراض أن الشخصيات الـ16 أصبحت متوفرة في المستودع.

أي من هذه الأعمال يحتاج مراجعة النطاق والملفات المتأثرة، ثم تنفيذًا مرحليًا وفق الموافقات المطلوبة.

## 8) القرار المطلوب قبل بدء التنفيذ

قبل بدء المرحلة A/B، يلزم اعتماد:
1. خريطة حقول ملف التقدم المحلي وسياسة كل حقل.
2. قائمة معرفات الشخصيات الـ16 وربطها بالأصول النهائية.
3. نموذج ملف اللاعب الخادمي وإصداراته.
4. آلية تخزين الجلسة الآمنة المتوافقة مع نسخة Godot/Android المستخدمة.

**الخلاصة:** الأولوية هي تثبيت هوية خادمية واحدة ثم تحميل ملف اللاعب، ثم حفظ الشخصية الجاهزة، ثم ترحيل التقدم بأمان، وأخيرًا استعادة الجلسة الآمنة على Android. لا تُمس هوية المؤسس ولا تُفعّل الأنظمة المالية خلال هذه المراحل.
