# عقد خدمة الاقتصاد الخادمية — KING OF EGYPT CITY

**الحالة:** تصميم تقني مرجعي قبل التنفيذ؛ ليس API عاملًا أو خادمًا منشورًا.  
**التاريخ:** 13 نوفمبر 2026  
**المرجع:** `OFFICIAL_ECONOMY_MASTER_AR.md`، و`ECONOMY_DEPENDENCY_INVENTORY_AR.md`، و`ECONOMY_PERSISTENCE_MIGRATION_PLAN_AR.md`، و`EVENTS_SERVER_CONTRACT_AR.md`.

## 1. الغرض وحدود هذا العقد

تحديد واجهة موحدة بين عميل Godot وخدمة الاقتصاد، بحيث تكون الخدمة الخادمية وحدها صاحبة القرار في:
- أرصدة Cash وChips وGems.
- استحقاق المكافآت والخصومات والأسعار.
- ملكية المركبات والألوان والأصول الاقتصادية.
- تقدم الأنشطة الذي يؤدي إلى مكافأة، وإيصالات المطالبات.
- وقت اليوم والاستحقاقات اليومية ومنع التكرار.

XP خبرة وتقدم منفصلان عن العملات الثلاث. لا يضيف العقد عملة رابعة، ولا تداولًا بين اللاعبين، ولا يحدد أسعارًا أو مكافآت جديدة.

**لا يختار هذا العقد مزود استضافة أو قاعدة بيانات أو نظام مصادقة أو بروتوكول نقل.** يجب اعتماد البنية التحتية أولًا؛ وتظل أسماء المسارات أدناه أسماء منطقية محايدة قابلة للمواءمة مع المزود المعتمد لاحقًا.

## 2. قواعد الثقة الإلزامية

1. يستخرج الخادم `player_id` من جلسة مصادق عليها؛ لا يقبل هوية يحددها العميل في جسم طلب يغير الاقتصاد.
2. لا يثق الخادم في رصيد أو سعر أو مبلغ مكافأة أو XP أو مستوى أو ملكية أو وقت أو نتيجة يرسلها العميل.
3. يرسل العميل نية الفعل ومعرفات المرجع و`request_id` فقط. يحسب الخادم السعر والاستحقاق والنتيجة من كتالوجه وحالة الحساب وقواعده.
4. كل تغيير اقتصادي وكل مطالبة مكافأة تنفذ ذريًا: إما ينجح الخصم/الإضافة وتحديث الملكية/التقدم والإيصال وسجل المعاملة جميعًا، أو لا يتغير أي منها.
5. كل طلب تغيير يستخدم `request_id` فريدًا ثابتًا عند إعادة المحاولة. الطلب المكرر يعيد النتيجة المسجلة ولا ينفذ مرة ثانية.
6. الوقت الموثوق هو وقت الخادم. لا تستخدم ساعة الجهاز أو تاريخ العميل لتجديد اليوم أو تحديد الاستحقاق.
7. لا يعلن العميل النجاح ولا يحدث الرصيد النهائي إلا بعد رد خادمي موثوق.
8. عند انقطاع الاتصال لا ينفذ العميل عمليات شراء أو مكافآت مؤقتة بغرض مزامنتها لاحقًا. يمكنه عرض آخر رصيد معروف مع وسم أنه غير محدث، وتعطيل التغييرات الاقتصادية حتى عودة الاتصال.
9. لا أسرار أو مفاتيح إدارية أو مفاتيح قاعدة بيانات داخل APK.
10. كل عملية إدارية أو منحة استثنائية تحتاج صلاحية خادمية وسجل تدقيق مستقل؛ لا يوجد تعديل رصيد من الواجهة مباشرة.

## 3. نموذج البيانات المنطقي

هذه كيانات مطلوبة على مستوى المفهوم. أسماء الجداول والأنواع النهائية يحددها اختيار قاعدة البيانات.

### 3.1 حساب الاقتصاد — `economy_account`

| الحقل | الغرض |
|---|---|
| `player_id` | مفتاح الحساب الثابت، فريد ومرتبط بهوية الخادم |
| `cash_balance` | رصيد Cash كعدد صحيح |
| `chips_balance` | رصيد Chips كعدد صحيح |
| `gems_balance` | رصيد Gems كعدد صحيح |
| `xp_total` | الخبرة، منفصلة عن العملات |
| `account_version` | رقم متزايد لمراجعة التحديثات المتزامنة |
| `created_at`, `updated_at` | وقت UTC من الخادم |

تستخدم الأرصدة أعدادًا صحيحة موقعة 64-bit في كل طبقات الحساب والتخزين. لا يعني ذلك اعتماد الحد الأقصى التقني كحد اقتصادي. يحدد السقف الاقتصادي بعد مراجعة رسمية منفصلة. يمنع استخدام floating point. وإذا كانت طبقة النقل لا تحفظ 64-bit بدقة، ترسل الأرصدة كسلاسل عشرية معيارية وتتحقق منها الخدمة.

### 3.2 سجل المعاملات — `economy_transaction`

سجل تدقيق غير قابل للتعديل العادي، ويحتوي على الأقل:
- `transaction_id` معرف فريد للعملية.
- `player_id` صاحب العملية.
- `request_id` مفتاح منع التكرار.
- `operation_type`: credit / debit / purchase / reward / claim / correction.
- `currency`: cash / chips / gems أو null لعملية XP/ملكية فقط.
- `amount`: قيمة صحيحة موجبة؛ واتجاهها في `direction` credit/debit.
- `reason_code` و`source_type` و`source_id`.
- `related_asset_id` عند الشراء أو الملكية.
- `balance_before` و`balance_after` للعملة المعنية.
- `server_timestamp` و`result` و`account_version`.
- مرجع إلى سجل المطالبة أو العملية التجارية المرتبطة.

تفرض قيود فريدة على `transaction_id` وعلى نطاق `(player_id, request_id)`. لا يسمح بتعديل سجل ناجح لإخفاء أثره؛ التصحيح يكون بمعاملة عكسية أو تصحيح إداري منفصل موثق، مع الاحتفاظ بالأصل.

### 3.3 مفاتيح منع التكرار — `idempotency_record`

تحتفظ بـ:
- `player_id`, `request_id`, `operation_scope`.
- بصمة canonical لطلب العميل بعد التحقق.
- الحالة: processing / succeeded / rejected.
- النتيجة النهائية التي يمكن إعادتها عند إعادة الطلب.
- `created_at`, `completed_at`.

إذا أعيد `request_id` نفسه مع جسم مختلف، يرفض الطلب كتعارض ولا يعاد تفسيره كعملية جديدة. يجب أن تكون مدة الاحتفاظ بالمفاتيح كافية لتغطية إعادة المحاولة ومراجعة السجلات؛ لا تحذف مفاتيح عمليات مالية ناجحة بطريقة تسمح بإعادة تنفيذها.

### 3.4 المطالبات والاستحقاقات — `reward_claim`

تسجل:
- `claim_id`, `player_id`, `claim_type`, `source_id`, `cycle_key`.
- `eligibility_snapshot` أو مراجع أحداث الإثبات الموثوقة.
- `transaction_id` الذي صرف المكافأة.
- الحالة ووقت الخادم.

تفرض قيود فريدة حسب نوع الاستحقاق. أمثلة النطاق: إنجاز محدد لكل لاعب، مهمة ذات إكمال وحيد، أو مكافأة يومية لكل لاعب ولكل يوم لعبة. لا تُخترع دورات أو تكرارات جديدة خارج القواعد المعتمدة.

### 3.5 الملكيات والتقدم

- `player_asset`: ملكية المركبات والألوان وغيرها من الأصول القابلة للامتلاك، مع قيد فريد يمنع امتلاك نسخة مكررة إذا كانت الملكية فريدة.
- `activity_progress`: حالة المهمة/الوظيفة/النشاط ومصدر الحدث ووقت الخادم.
- `achievement_progress`: تقدم الإنجازات وحالة الاستحقاق.
- `daily_activity_state`: أنشطة اليوم وفق مفتاح اليوم الخادمي.
- `economy_audit_log`: أحداث الإدارة والتصحيح والمراجعة.

لا تعتبر ملكية مرسلة من العميل إثباتًا؛ تستعلم الواجهة عن الملكية من الخدمة.

## 4. واجهة الخدمة المنطقية

جميع الطلبات تتطلب جلسة مصادقًا عليها. الأمثلة التالية وصف لعقد البيانات وليست مسارات منشورة أو أسماء SDK جاهزة.

### 4.1 قراءة الحالة

**منطقيًا:** `GET /economy/account`

لا يستقبل جسمًا يحدد اللاعب. يعيد:
- `player_id` من الجلسة.
- الأرصدة الثلاثة كقيم صحيحة/سلاسل عشرية آمنة.
- `xp_total` والمستوى المحسوب وفق نظام التقدم المعتمد.
- `account_version`.
- `server_time`.
- ملخص الملكيات عند الحاجة، أو مرجعًا لطلب منفصل لتقليل الحمولة.

القراءة لا تنشئ استحقاقًا ولا تصرف مكافأة.

### 4.2 طلب شراء

**منطقيًا:** `POST /economy/purchases`

طلب العميل:
- `request_id`
- `catalog_item_id`
- `catalog_version` إن كان إصدار الكتالوج مطلوبًا لتفادي شراء عنصر تغير تعريفه.

لا يقبل العميل `price` أو `currency` أو `player_id` أو علم `owned=true) كحقائق. الخادم يقرأ العنصر من كتالوج معتمد، يتحقق من السعر والعملة والأهلية والملكية والرصيد، ثم ينفذ الخصم وإضافة الملكية وإيصال العملية في معاملة واحدة.

إذا كان العنصر مملوكًا بالفعل، تعاد حالة واضحة ولا يحدث خصم ثانٍ. إذا كان السعر غير محدد أو العنصر غير منشور، يرفض الشراء؛ لا تخمين.

### 4.3 طلب إكمال نشاط أو وظيفة

**منطقيًا:** `POST /economy/activities/complete`

طلب العميل:
- `request_id`
- `activity_id`
- `activity_instance_id` أو مرجع جلسة/مهمة بدأها الخادم عند الحاجة.
- أدلة/أحداث تفاعل محددة مسبقًا في العقد، لا قيمة المكافأة.

الخادم يتحقق من بداية النشاط ومتطلباته وتسلسله ووقته وعدم إكماله سابقًا. لا يقبل `cash_reward` أو `chips_reward` أو `xp_reward` من العميل. بعد النجاح يحدث التقدم وXP والعملات والإيصال في معاملة واحدة.

### 4.4 المطالبة بمكافأة يومية أو إنجاز

**منطقيًا:** `POST /economy/rewards/claim`

طلب العميل:
- `request_id`
- `claim_type`
- `source_id` أو `cycle_id` الذي يعرّف الاستحقاق المعتمد.

الخادم يحدد يوم اللعبة من توقيته وإعداد المنطقة الزمنية المعتمد، ويتحقق من الشروط ومن عدم وجود مطالبة سابقة. قراءة حالة الاستحقاق منفصلة عن المطالبة. لا تمنح الواجهة المكافأة بمجرد إظهار زر الاستلام.

### 4.5 استعلام حالة طلب

**منطقيًا:** `GET /economy/requests/{request_id}`

يستخدم بعد timeout أو انقطاع الاتصال. يعيد النتيجة النهائية للطلب نفسه لصاحب الجلسة. لا ينشئ عملية جديدة ولا يغير الرصيد.

### 4.6 قراءة سجل اللاعب

**منطقيًا:** `GET /economy/transactions?cursor=...`

يعيد سجلات اللاعب الحالي فقط مع pagination. لا يسمح بطلب سجل لاعب آخر عبر تغيير معرف في query. تعرض الواجهة بيانات السجل للقراءة فقط.

## 5. بروتوكول تنفيذ المعاملة الذرية

داخل وحدة معاملة واحدة في قاعدة البيانات أو آلية ذرية مكافئة:

1. تحقق من الجلسة واستخرج `player_id`.
2. تحقق من صحة `request_id` ونطاق العملية وبصمة الطلب.
3. افحص مفتاح منع التكرار. إذا كان مكتملًا، أعد النتيجة المحفوظة كما هي.
4. احجز مفتاح الطلب للحالة قيد المعالجة بطريقة تمنع السباق بين الطلبات المتزامنة.
5. اقفل سجل الحساب أو استخدم تحديثًا شرطيًا بـ`account_version` لمنع ضياع تحديثات الرصيد.
6. احسب السعر/الاستحقاق من بيانات الخادم. تحقق من الرصيد والحدود والملكية والأهلية.
7. نفذ الخصم/الإضافة وتحديث XP/التقدم/الملكية وسجل المعاملة وسجل المطالبة ومفتاح الطلب ضمن commit ذري واحد.
8. احفظ النتيجة النهائية والنسخة الجديدة للحساب.
9. أعد الرصيد والنسخة والنتيجة من الخادم.

**حالات الفشل:** عدم كفاية الرصيد، سعر غير معروف، ملكية سابقة، انتهاء الجلسة، عدم الأهلية، تعارض نسخة الحساب، تكرار الطلب، أو فشل التخزين. عند فشل المعاملة لا يبقى خصم منفصل أو ملكية منفصلة أو استحقاق مستهلك. إذا انقطع الاتصال بعد نجاح الخادم، يستعلم العميل عن نفس `request_id`.

## 6. قواعد العملة والاستحقاق

- العملات المسموحة: Cash وChips وGems فقط. XP خارج جدول العملات.
- كل عنصر/نشاط له عملة وسعر/مكافأة صريحة من مرجع رسمي. لا يستنتج الخادم أن كل متجر يقبل كل العملات.
- لا تداول ولا تحويل عملات ولا هدايا عناصر بين اللاعبين.
- الهدية الاجتماعية — إن رُبطت — تظل هدية واحدة يوميًا إجمالًا من اللاعب إلى صديق واحد، Cash أو Chips فقط، مع خصم وإضافة وسجل للطرفين في معاملة ذرية؛ لا Gems ولا عناصر. لا ينفذ هذا المسار قبل وجود قرار ومصدر تنفيذي معتمد.
- صناديق الدخول اليومية منفصلة عن مكافأة الأنشطة اليومية.
- مكافأة البازل الكبرى 1,000 Gems تصرف مرة واحدة بعد تحقق الخادم من إكمال الصورة الكاملة. لا يحدد العقد مكافآت مراحل القطع أو احتمالات سقوطها.
- الحفلة تكلف 150 Gems ومدتها 20 ثانية وفق القرار المعتمد؛ إنشاء الحفلة والخصم عملية ذرية. مكافآت المشاركة لا تمنح لمجرد الوقوف، وتحتاج مشاركة فعلية وسقفًا مرتبطًا بمستوى اللاعب وفق قواعد معتمدة لاحقًا. لا يفرض حد أقصى اعتباطي للمشاركين.
- الكازينو: الرهان Chips، والفوز يمنح Cash، والخسارة تخصم Chips؛ لا يحدد هذا العقد مبالغ أو نسبًا أو سقفًا يوميًا لم تعتمد.
- لا تمنح عمليات تصحيح أو إدارة رصيدًا إلا بصلاحية خادمية وسبب موثق وموافقة حسب سياسة الإدارة.

## 7. كتالوج الأسعار

يكون الكتالوج على الخادم فقط، بإصدار منشور ومراجعة تغييره. الحد الأدنى لحقوله:
- `catalog_item_id`, `item_type`, `status`.
- `currency`, `price` أو حالة صريحة `not_for_sale`.
- شروط المستوى/الأهلية عند وجودها.
- مرجع تعريف العنصر والملكية الناتجة.
- `catalog_version`, `effective_at`, `updated_by`.

لا تُنقل الأسعار المتعارضة أو غير المفعلة من الكود إلى الكتالوج تلقائيًا. لا تغيير بأثر رجعي على المعاملات أو أرصدة اللاعبين. أي تعديل مستقبلي يحتاج إصدارًا جديدًا وتوثيقًا ومراجعة أثر.

## 8. ربط العميل الحالي

| المصدر الحالي | مسؤولية العميل بعد الربط |
|---|---|
| `WalletManager` | يصبح واجهة عميل/ذاكرة عرض مؤقتة تتلقى الحالة من الخدمة؛ لا ينشئ رصيدًا نهائيًا |
| `MissionManager` | يدير الحركة والتفاعل المحلي؛ يطلب إكمال النشاط من الخادم ولا يحدد المكافأة |
| `DailyActivities` | يعرض حالة اليوم من الخادم ويرسل طلب مطالبة؛ لا يعتمد ساعة الجهاز |
| `AchievementManager` | يعرض تقدم/استحقاقات الخادم ولا يمنح العملات محليًا |
| `VehicleStoreManager` | يعرض كتالوج الخادم ويرسل `catalog_item_id` و`request_id`؛ لا يقرر السعر أو الملكية |
| `CityHUD` والملف الشخصي | عرض الأرصدة ونتيجة المعاملة فقط؛ لا كتابة مباشرة |
| `ProfileSettings` | لا يكتب فوق سجل الاقتصاد أو الملكية؛ فصل الإعدادات عن بيانات الحساب |
| `camp_animal_staff.gd` | لا يبدأ التأجير قبل نجاح طلب الخدمة؛ لا يعتمد معرفات محلية مؤقتة كضمان وحيد |

لا يُحذف Autoload الحالي ولا ملفات الحفظ القديمة خلال هذه الخطوة. لا تستمر كتابة مستقلة مزدوجة إلى `profile.*` و`wallet.*` بعد بدء الانتقال.

## 9. خطة الترحيل والانتقال

1. **تثبيت خط الأساس:** حفظ نسخ المصدر ومخطط الحفظ وبصمة الملفات والملكية والإيصالات قبل أي تعديل.
2. **بناء الخدمة في بيئة اختبار:** لا بيانات لاعبين حقيقية، ولا اتصال ببيئة الإنتاج.
3. **محلل قديم للقراءة فقط:** قراءة `wallet.*` و`profile.*` دون تعديل المصدر. أي تعارض في المال أو الرقائق يعزل للمراجعة؛ لا جمع ولا اختيار الأكبر.
4. **ترحيل تجريبي idempotent:** تشغيله مرتين على بيانات اختبار ومقارنة الأرصدة والملكية وXP والتقدم والإيصالات.
5. **وضع مقارنة دون كتابة مزدوجة:** يمكن مقارنة نتيجة حساب العميل مع نتيجة الخدمة في بيئة اختبار/مراقبة معزولة، لكن لا يعتمد رصيد العميل ولا تُنفذ عمليتان اقتصاديتان مستقلتان.
6. **ربط تدريجي:** تبدأ القراءة من الخدمة بعد التحقق؛ ثم تربط العمليات حسب مجموعات الاختبار. لا تُفتح عمليات offline التي تتطلب خصمًا أو مكافأة.
7. **تحويل معتمد:** بعد نجاح جميع البوابات، وخطة رجوع مجربة، ومراجعة أثر، وموافقة صريحة على الإصدار.
8. **إيقاف التوافق القديم:** لا يتم إلا بعد ثبوت عدم وجود مستهلكين، وتأكيد سلامة البيانات، وفترة تحقق مناسبة.

## 10. مصفوفة الاختبار الإلزامية

| الاختبار | النتيجة المطلوبة |
|---|---|
| نفس الطلب مرتين بالتتابع | معاملة واحدة ونتيجة واحدة |
| نفس الطلب بالتوازي | لا خصم أو مكافأة مزدوجة |
| نفس request_id مع جسم مختلف | رفض تعارض |
| طلبان مختلفان لشراء آخر رصيد | لا يتجاوز الرصيد ولا تنشأ ملكية دون خصم |
| انقطاع بعد commit وقبل الرد | استعلام request_id يعيد نجاح العملية دون تكرار |
| فشل قبل commit | لا أثر على الرصيد أو الملكية أو الاستحقاق |
| رصيد غير كافٍ | رفض دون خصم |
| سعر غير محدد أو عنصر غير منشور | رفض دون تخمين |
| شراء أصل مملوك مسبقًا | لا خصم ثانٍ |
| تغيير ساعة الهاتف | لا يغير اليوم أو الاستحقاق |
| إعادة تشغيل/تبديل جهاز | الحالة الخادمية نفسها |
| عميل معدل يرسل مبلغًا أو عملة أو player_id مزورًا | تجاهل/رفض الحقول غير الموثوقة |
| محاولة قراءة سجل لاعب آخر | رفض صلاحيات |
| قيم أكبر من 2 مليار وحتى نطاق التريليونات | دقة كاملة في الحساب والتخزين والنقل والعرض |
| Overflow أو مبلغ سالب أو صفر غير مسموح | رفض آمن |
| ترحيل الحساب مرتين | لا مضاعفة ولا فقد |
| فشل ترحيل جزئي ثم استعادة | عودة كاملة للأرصدة والملكية والتقدم والإيصالات |
| تصحيح إداري | صلاحية موثقة، سبب، سجل تدقيق، معاملة عكسية واضحة |

كل الاختبارات تستخدم حسابات وبيانات اختبار اصطناعية فقط.

## 11. شروط فتح التنفيذ

لا يبدأ تنفيذ التكامل الفعلي قبل تحقق كل ما يلي:
- [ ] اختيار واعتماد مزود الاستضافة وقاعدة البيانات والمصادقة والنقل.
- [ ] نشر بيئة اختبار معزولة وصلاحياتها وأسرارها خارج التطبيق.
- [ ] اعتماد مخطط الحساب والمعاملات ومفاتيح idempotency والقيود الفريدة.
- [ ] وجود API موثق ومختبر، لا مجرد أسماء مسارات في مستند.
- [ ] اعتماد كتالوج الأسعار دون تعارضات غير محسومة.
- [ ] خطة ترحيل واسترجاع ومطابقة مجربة على حسابات اصطناعية.
- [ ] اجتياز اختبارات التزامن وانقطاع الشبكة وإعادة المحاولة والأرقام الكبيرة.
- [ ] ربط كل مستهلك حالي ومنع الكتابة المزدوجة أو منح المكافآت محليًا.
- [ ] مراجعة أمنية ثم اختبار Godot وAndroid فعلي.
- [ ] موافقة صريحة قبل أي إطلاق أو تغيير على بيانات حقيقية.

## 12. ما لا يثبته هذا المستند

هذا المستند لا يثبت وجود خادم أو قاعدة بيانات أو API أو مصادقة أو معاملات ذرية منفذة. لا يوجد اختيار لمزود، ولا كود تشغيل جديد، ولا أسعار أو مكافآت جديدة. إنه عقد تصميم يحدد شروط التنفيذ والاختبار ويمنع الادعاء بالجاهزية قبل إثباتها.

**قرار السلامة النهائي:** لا تُنقل أي أرصدة حقيقية ولا تُعدل الأسعار ولا يُحذف أي حفظ محلي ولا يُدمج PR إلى `main` بناءً على هذه الوثيقة وحدها.
