# مراجعة أمان خدمة استحقاق المؤسس

**التاريخ:** 2026-11-25  
**الفرع:** `feature/build-environment-separation-review`  
**طلب المراجعة:** PR #161 (Draft)  
**الحالة:** تحسين المصدر وإضافة اختبارات؛ لم يتم نشر الوظيفة على أي مشروع Supabase.

## 1) الحالة الفعلية للوظيفة

مصدر الوظيفة موجود في `supabase/functions/founder-entitlement/index.ts` في المستودع. لكن فحص Edge Functions الحالي أظهر:

- TEST: لا توجد وظيفة منشورة باسم `founder-entitlement` ضمن الوظائف النشطة.
- PRODUCTION: لا توجد وظيفة منشورة باسم `founder-entitlement` ضمن الوظائف النشطة.

وجود المصدر في Git لا يعني أن رابط الوظيفة متاح في أي بيئة.

## 2) تدفق الاعتماد المعتمد

1. يرسل عميل اللعبة access token الناتج من جلسة Supabase Auth في `Authorization: Bearer`.
2. ترسل اللعبة مفتاح publishable الخاص بالبيئة في ترويسة `apikey` فقط.
3. تتحقق بوابة Edge Function من JWT أولًا (`verify_jwt = true`).
4. تستعلم الوظيفة عن `/auth/v1/user` باستخدام رمز الجلسة نفسه، ولا تثق في UUID أو البريد أو المطالبات التي يرسلها العميل.
5. لا تصدر تذكرة إلا إذا تطابق UUID الخادمي المسموح به والبريد المعتمد، وكان البريد مؤكدًا.
6. توقع الوظيفة مطالب المؤسس بمفتاح RSA خاص محفوظ في أسرار Edge Function، وتعيد النص الأصلي والتوقيع.
7. يتحقق عميل Godot من التوقيع بالمفتاح العام المضمّن، ثم يطابق `subject_id` مع حساب اللاعب النشط قبل تفعيل هوية المؤسس.

تذكرة Offline مدتها 30 يومًا. وهي إثبات هوية محلي فقط، ولا تمنح وحدها صلاحيات إدارة خادمية.

## 3) التغييرات على هذا الفرع

- جعل معالج الوظيفة قابلًا للاختبار بحقن البيئة وطلب Auth والوقت.
- رفض أي جسم طلب لا يطابق كائن JSON فارغًا صغيرًا؛ لا يقبل العميل تمرير subject أو claims.
- التحقق من شكل عنوان Supabase ومفتاح publishable وUUID والبريد قبل الاتصال.
- التحقق من استجابة Auth وأن `email_confirmed_at` قيمة نصية غير فارغة.
- الإبقاء على رسائل الخطأ عامة، دون كشف تفاصيل الشبكة أو المفتاح الخاص.
- إضافة اختبارات Deno لحالات OPTIONS وطرق HTTP والرمز المفقود/غير الصحيح، والتهيئة الناقصة، وهوية غير مطابقة، وبريد غير مؤكد، ونجاح التوقيع والتحقق منه، وأخطاء الشبكة والتوقيع.
- تغيير إعداد الوظيفة في `supabase/config.toml` إلى `verify_jwt = true`؛ لأن الطلب يحمل access token حقيقيًا في Authorization. يظل فحص `/auth/v1/user` داخل الوظيفة قائمًا كتحقق إضافي من هوية المؤسس.

## 4) الأسرار المطلوبة لكل بيئة

يجب إعدادها يدويًا وبشكل مستقل في TEST وPRODUCTION عند وقت النشر:

- `FOUNDER_AUTH_USER_ID`: UUID حساب Auth الأصلي للمؤسس في البيئة نفسها.
- `FOUNDER_AUTH_EMAIL`: البريد المؤكد المرتبط بذلك الحساب.
- `FOUNDER_SIGNING_PRIVATE_KEY`: مفتاح RSA خاص بصيغة PEM/PKCS#8.

`SUPABASE_URL` و`SUPABASE_PUBLISHABLE_KEYS` يوفّرهما Supabase تلقائيًا داخل Edge Functions؛ لا حاجة إلى تخزين service-role أو secret API key في الوظيفة الحالية.

يجب مطابقة المفتاح العام المضمّن في Godot مع المفتاح الخاص في كل بيئة قبل النشر. لا ترسل قيم الأسرار أو المفتاح الخاص في المحادثة.

## 5) حدود يجب عدم تجاوزها

- لا يتم نشر الوظيفة إلى TEST أو PRODUCTION ضمن هذا PR.
- لا يتم تغيير حساب المؤسس أو UUID أو البريد أو صلاحياته.
- لا يتم تعديل قاعدة البيانات أو Auth أو سياسات RLS.
- لا يتم إصدار صلاحيات إدارية من التذكرة المحلية. كل عملية إدارية Online يجب أن تتحقق خادميًا بصورة مستقلة.
- صلاحية Offline البالغة 30 يومًا لا يمكن إبطالها فورًا بعد إصدارها؛ أي إجراء حساس يجب ألا يعتمد على التذكرة المحلية وحدها.

## 6) بوابة القبول التالية

1. نجاح Godot CI واختبارات Deno على آخر commit.
2. نشر منفصل إلى TEST بعد التأكد من وجود الأسرار ومطابقة زوج المفاتيح، وبموافقة منفصلة.
3. اختبار طرف إلى طرف بحساب المؤسس الأصلي فقط: تسجيل الدخول، التحقق من البريد، إصدار التذكرة، التحقق من RSA، التخزين المؤقت، رفض حساب آخر.
4. عدم الانتقال إلى PRODUCTION قبل توثيق نجاح TEST ومراجعة إعدادات الأسرار والمفتاح العام.
