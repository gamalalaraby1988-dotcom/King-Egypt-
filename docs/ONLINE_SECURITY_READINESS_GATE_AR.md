# بوابة الأمان والجاهزية للأونلاين
## KING OF EGYPT CITY

**الحالة:** معيار أمان إلزامي قبل فتح اللعبة للاعبين الحقيقيين — مواصفة وتدقيق، وليست تنفيذًا لخادم أو إثباتًا لاجتياز الاختبارات.
**الفرع:** `sync-latest-approved-decisions-77-79`
**التاريخ:** 13 نوفمبر 2026

## 1. القرار الأمني الأساسي

اللعبة مستهدفة للعب الجماعي عبر الإنترنت. لذلك جهاز اللاعب وتطبيق Godot وملفات `user://` وطلبات الشبكة كلها مصادر غير موثوقة. الخادم وقاعدة بياناته هما مصدر الحقيقة الوحيد للحسابات والوقت والأرصدة والخبرة والملكية والتقدم والاستحقاقات والصلاحيات ونتائج الأنشطة.

لا تُعد حماية ملف محلي أو تشفيره أو إخفاء أزرار الواجهة أو إضافة تحقق داخل العميل حماية اقتصادية ضد لاعب يملك جهازه أو نسخة معدلة من التطبيق. لا يجوز اعتماد أي قيمة يرسلها العميل باعتبارها حقيقة لمجرد أن النسخة الرسمية أرسلتها.

**حالة المصدر التي تم التحقق منها:** المشروع الحالي يحتوي على أنظمة Godot محلية وملفات حفظ محلية، ولا يحتوي في الشجرة المفحوصة على backend أو قاعدة بيانات خادمية أو طبقة مصادقة/جلسات موثوقة مكتملة. كما أن واجهات المجموعات والتواصل المشار إليها في وثيقة التكامل ما زالت محلية. نجاح CI الحالي يثبت فحوصات Godot المحددة فقط، ولا يثبت وجود أونلاين أو أمان خادمي.

## 2. نموذج التهديد

يجب تصميم النظام على افتراض أن اللاعب أو المهاجم يستطيع:
- تعديل ملفات الحفظ المحلية أو حذفها أو إعادتها إلى نسخة أقدم.
- تعديل التطبيق أو تشغيل عميل معدل أو استدعاء واجهات الشبكة خارج الواجهة.
- إعادة إرسال الطلب نفسه، أو إرسال طلبات متزامنة، أو تغيير ترتيبها.
- تزوير المبلغ أو السعر أو المكافأة أو المستوى أو وقت الجهاز أو نتيجة النشاط في الطلب.
- قطع الاتصال قبل/بعد تنفيذ العملية ثم إعادة المحاولة.
- انتحال هوية لاعب آخر أو استخدام جلسة مسروقة أو منتهية.
- إرسال رسائل وروابط ومحتوى مزعج، أو استغلال حدود الدعوات والبلاغات والفعاليات.
- محاولة تجاوز صلاحيات المؤسس أو المشرف أو الوصول إلى بيانات لاعب آخر.

## 3. ما يجب أن يبقى خادميًا حصريًا

لا يسمح للعميل بأن يقرر أو يثبت أيًا مما يلي:
1. إنشاء الحساب و`player_id` الثابت، والتحقق من تسجيل الدخول وإصدار الجلسة وإبطالها.
2. الأرصدة الثلاثة Cash / Chips / Gems، وXP منفصلة، وأي تعديل لها.
3. أسعار المنتجات والرسوم والخصومات والمكافآت والحدود والاستحقاقات.
4. ملكية المركبات والألوان والحيوانات والأثاث ومحتويات الشقة وأي عنصر دائم.
5. أهلية المهام والوظائف والإنجازات والصناديق اليومية والأسبوعية والزيارات والحفلات والبطولات والبازل.
6. اليوم والأسبوع والموسم والوقت المتبقي وتاريخ تغيير الاسم؛ جميعها بتوقيت الخادم.
7. نتائج المسابقات والفوز والخسارة والمشاركة الفعلية ومكافحة التكرار.
8. الأدوار وصلاحيات المؤسس والإعلانات والإجراءات الإدارية.
9. الدعوات وقبولها وحدود المجموعة والزوار والطرد والهدية اليومية.
10. حفظ سجل المعاملات والإيصالات وسجل التدقيق.

العميل يرسل **نية الفعل ومعرفات مرجعية فقط**، مثل `claim_reward` مع `request_id` ومرجع المهمة. لا يرسل مبلغ المكافأة الذي يقرره، ولا رصيدًا جديدًا، ولا سعرًا، ولا `player_id` يختاره لنفسه، ولا نتيجة نهائية يريد فرضها.

## 4. عقد المعاملة الاقتصادية

كل تغيير اقتصادي يجب أن يمر بمعاملة قاعدة بيانات ذرية واحدة:
- التحقق من جلسة اللاعب وربطها بهوية الحساب من الخادم.
- التحقق من نوع العملية ومصدرها وأهلية اللاعب وفق بيانات الخادم.
- جلب السعر/المكافأة من كتالوج وقواعد خادمية، لا من قيمة العميل.
- استخدام أعداد صحيحة دقيقة 64-bit أو تمثيل عشري نصي canonical عند عبور وسيط لا يحفظ الدقة. يمنع float للأرصدة.
- التحقق من كفاية الرصيد ومن عدم تجاوزه الحدود المعتمدة.
- كتابة الرصيد والملكية/التقدم والاستحقاق والإيصال وسجل التدقيق في commit واحد.
- قيد فريد على `request_id` أو `transaction_id` ضمن نطاق اللاعب والعملية؛ إعادة الطلب تعيد النتيجة السابقة ولا تنفذ مرة أخرى.
- استخدام قفل/تحكم تزامن مناسب حتى لا تنجح عمليتا شراء معًا اعتمادًا على الرصيد نفسه.
- عدم استهلاك استحقاق أو محاولة تغيير اسم إذا فشل commit.
- عدم قبول أي نجاح من العميل قبل تأكيد الخادم.

لا يُعتمد سقف 2,000,000,000 الموجود في WalletManager المحلي كسقف اقتصادي مستهدف. كما لا يُستبدل بسقف آخر قبل قرار اقتصادي مستقل. الحد التقني signed int64 ليس سقفًا اقتصاديًا.

## 5. الهوية والجلسات والنقل

- إنشاء `player_id` عشوائي ثابت من الخادم؛ اسم العرض ليس معرف الحساب.
- مصادقة حقيقية، جلسات قصيرة العمر قابلة للإبطال والتدوير، وحماية من إعادة استخدام refresh/session tokens.
- نقل مشفر عبر TLS مع التحقق من الشهادة؛ لا أسرار backend أو مفاتيح إدارية أو مفاتيح توقيع ثابتة داخل APK.
- صلاحيات أقل ما يمكن لكل خدمة ومهمة تشغيلية، وفصل صلاحيات المؤسس عن حساب اللاعب العادي.
- حماية من brute force وتعداد الحسابات، مع حدود محاولات وتباطؤ مناسب دون كشف وجود الحساب.
- عدم تسجيل كلمات المرور أو الرموز السرية أو بيانات الجلسات في السجلات.
- لا يُعتبر تثبيت عنوان API أو إخفاؤه أو obfuscation بديلًا للمصادقة والتفويض.

## 6. مكافحة الغش وحدود اللعب

- التحقق الخادمي من انتقالات الحالة ومعدلات الحركة والمسافة والسرعة والتوقيت وتسلسل التفاعل عند تأثيرها في الجوائز أو المنافسة.
- لا يقبل الخادم أحداثًا مستحيلة أو خارج نطاق العالم/النشاط أو متكررة.
- تحديد معدل الطلبات لكل حساب/جلسة/IP وفق نوع العملية، مع حدود مستقلة للرسائل والدعوات والبلاغات ومحاولات المطالبة.
- لا يمنح الخادم مكافأة لمجرد رسالة `complete` من العميل؛ يتحقق من مصدر الحدث وتتابعه وأهلية المشاركة.
- لا تعتمد مدة الحفلة ذات 7 ثوانٍ أو عدادات الواجهة على ساعة العميل؛ وقت البدء والانتهاء يصدر من الخادم.
- لا يُعتمد client-side anti-cheat كحاجز أمني وحيد. يستخدم كإشارة مساعدة فقط.
- لا تضف نظام تداول بين اللاعبين؛ قرار المشروع الحالي يمنع البيع والشراء/التداول بينهم.

## 7. الدردشة والمحتوى الاجتماعي

- التحقق من الجلسة وعضوية المجموعة/الغرفة وصلاحية الإرسال في كل رسالة.
- تطبيق حدود الطول المعتمدة، وتحديد معدل الإرسال، وتنقية/ترميز النص عند عرضه لمنع حقن النصوص أو الروابط الضارة.
- توفير كتم/حظر/بلاغ وإجراءات مراجعة إدارية خادمية، مع سجل محدود الوصول للأحداث اللازمة للسلامة.
- عدم كشف بيانات حساب أو موقع/جلسة لاعب لغير المصرح لهم.
- لا تسمح الدعوة أو الطرد أو إدارة الشقة إلا لصاحب الصلاحية وفق حالة الخادم؛ لا تثق بقائمة أصدقاء أو زوار مرسلة من العميل.

## 8. قاعدة البيانات والتشغيل

- فصل بيئات التطوير والاختبار والإنتاج وحسابات الخدمة وبياناتها؛ يمنع استخدام بيانات اللاعبين الحقيقيين في الاختبارات.
- نسخ احتياطية مشفرة ومجدولة، مع اختبار استعادة فعلي دوري وقياس RPO/RTO قبل الإطلاق.
- سجل تدقيق append-only للعمليات الإدارية والاقتصادية الحساسة؛ صلاحيات قراءة محدودة ومراقبة للتعديلات.
- مراقبة معدلات فشل الدخول، وتكرار الطلبات، وتضارب الأرصدة، وعمليات الرفض غير المعتادة، ومعدلات الرسائل.
- تنبيهات للحوادث الاقتصادية والأمنية، وخطة إيقاف/تعطيل عمليات حساسة دون حذف بيانات.
- إدارة الأسرار خارج المستودع وCI artifacts وAPK؛ تدوير المفاتيح وإبطالها عند الاشتباه.
- تحديد سياسة الاحتفاظ بالبيانات والخصوصية والحذف وفق المتطلبات القانونية ومكان الاستضافة قبل الإطلاق.
- لا تُسجل معلومات شخصية غير لازمة، ولا تعرض بيانات لاعب في استجابة API إلا بالحد الأدنى.

## 9. قواعد العميل والحفظ المحلي

- تبقى ملفات ConfigFile المحلية cache/تفضيلات/حالة مؤقتة فقط، ولا تثبت رصيدًا أو ملكية أو مكافأة أو صلاحية.
- لا يسمح بتشغيل تدفق اقتصادي موثوق عند فشل الاتصال بالخادم؛ يمكن عرض آخر لقطة قراءة على أنها قديمة، لكن يمنع الصرف والشراء والمطالبة والمزايا التي تتطلب تحققًا.
- يجب ألا تكتب إعدادات ProfileSettings نسخة ConfigFile قديمة فوق بيانات اقتصادية أحدث. توحيد/فصل إعدادات العرض المحلية عن سجل الحساب الخادمي يسبق إزالة مسارات الحفظ القديمة.
- لا تُحذف ملفات الحفظ التاريخية ولا تُختار قيمة أعلى عند تعارض مصادر المال/الرقائق. تُعزل الحالة للمراجعة، وتُحفظ نسخة وبصمة ومصدر القيم.
- لا تستخدم إيصالات محلية كدليل مطالبة أو كمرجع لمنح تعويض تلقائي.

## 10. بوابات ما قبل إطلاق الأونلاين

لا يُعلن عن اللعبة أنها جاهزة أونلاين ولا تفتح اقتصادًا حقيقيًا قبل اجتياز جميع البوابات التالية:

| البوابة | شرط النجاح |
|---|---|
| S0 — بنية الخادم | backend وقاعدة بيانات وبيئات تشغيل فعلية، مع توثيق مالك الخدمة وخطة الاستضافة |
| S1 — الحساب | تسجيل/مصادقة/جلسات/إبطال/ربط player_id، واختبارات انتحال وانتهاء الجلسة |
| S2 — الاقتصاد | معاملات ذرية، idempotency، تزامن، أسعار خادمية، سجل تدقيق، واسترجاع |
| S3 — التقدم | مهام وإنجازات ويوميات ومواسم بتوقيت وأهلية خادميين |
| S4 — الملكيات | مركبات وألوان وممتلكات وشقة لا يمكن إنشاؤها أو نسخها من العميل |
| S5 — اجتماعي | مجموعات ودعوات ودردشة وشقة وصلاحيات وحدود ومكافحة إساءة الاستخدام |
| S6 — أمن الشبكة | TLS، أسرار خارج العميل، rate limiting، تحقق مدخلات، ومراجعة صلاحيات |
| S7 — اختبارات هجومية | إعادة الطلب، طلبات متزامنة، replay، تزوير قيم، انقطاع قبل/بعد commit، جلسات مسروقة، وعبث بالعميل |
| S8 — الاستعادة | استعادة نسخة احتياطية مجربة ومطابقة حسابات/أرصدة/ملكيات بعد الاستعادة |
| S9 — Android | اختبار على أجهزة Android فعلية، شبكة ضعيفة، انتقال بين Wi-Fi/بيانات، انقطاع وإعادة اتصال |
| S10 — تشغيل محدود | اختبار مغلق بحسابات اختبار ومراقبة وسجلات وخطة إيقاف، قبل أي فتح عام |

كل بوابة تتطلب دليلًا قابلًا للمراجعة (كود، إعدادات، سجل CI، أو تقرير اختبار). لا تُعد الوثيقة وحدها اجتيازًا.

## 11. ترتيب التنفيذ الأكثر أمانًا

1. اعتماد هذه البوابة كشرط إطلاق، مع عدم تغيير الأسعار أو المكافآت أو بيانات اللاعبين.
2. اختيار مزود/بنية backend وقاعدة بيانات بعد مقارنة التكلفة والاعتمادية وموقع الاستضافة ومتطلبات التشغيل؛ لا يُخترع مزود أو سر أو endpoint.
3. تصميم مخطط الحساب والمعاملات والصلاحيات وعقود API قبل توصيل واجهات Godot.
4. تنفيذ الحساب والجلسات وسجل المعاملات أولًا، ثم الاقتصاد والملكية والتقدم.
5. بناء طبقة عميل تتصل بالخدمة، وتتعامل مع التحميل والرفض وإعادة المحاولة والمهلة وانقطاع الشبكة بأمان.
6. نقل كل نظام اقتصادي/اجتماعي إلى قرار خادمي تدريجيًا، مع إبقاء القراءة القديمة/النسخ الاحتياطي حتى نجاح المطابقة.
7. اختبارات أمن وتزامن واسترجاع، ثم اختبار Android وشبكات حقيقية، ثم إطلاق مغلق مراقب.
8. إزالة المسارات المحلية القديمة فقط بعد إثبات عدم وجود مستهلكين واجتياز الترحيل والرجوع.

## 12. محظورات أثناء التنفيذ

- لا دمج إلى `main` ولا حذف بيانات أو أرصدة أو ملكيات.
- لا تغيير لأسعار أو مكافآت غير معتمدة ولا إنشاء عملة جديدة.
- لا وضع أسرار أو مفاتيح إدارية في كود Godot أو ملفات APK.
- لا قبول رصيد/سعر/XP/ملكية/وقت/صلاحية من العميل.
- لا ادعاء أن اللعبة أونلاين لمجرد وجود واجهة دردشة أو مجموعات محلية.
- لا تشغيل اختبارات تمس ملف اللاعب الحقيقي؛ يجب عزل ملفات الاختبار وبياناتها.
- لا تفعيل المشتريات أو المطالبات الاقتصادية في بيئة متعددة اللاعبين قبل تحقق الخادم.

## 13. حالة هذا التدقيق

- **تم:** مراجعة وثيقة التكامل الشامل، عقد الفعاليات الخادمي، وثائق المحفظة والاقتصاد، جرد ملفات المشروع، ومراجعة مسارات الحفظ المحلية.
- **مؤكد:** لا يوجد backend مثبت في شجرة المشروع المفحوصة؛ الاقتصاد والحفظ الحاليان محليان، والأنظمة الاجتماعية المشار إليها محلية.
- **لم يتم:** بناء backend أو قاعدة بيانات أو مصادقة أو API أو نقل حسابات؛ لم تُجر اختبارات اختراق أو Android أو اتصال شبكي حقيقي.
- **قرار السلامة:** المشروع لا يجتاز حاليًا بوابة إطلاق أونلاين موثوق. يظل تطوير العالم والواجهات ممكنًا، لكن لا تُفتح معاملات اقتصادية أو ملكيات أو استحقاقات للاعبين الحقيقيين اعتمادًا على العميل.
